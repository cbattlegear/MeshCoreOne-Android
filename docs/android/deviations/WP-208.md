# WP-208 native messaging adaptations

## Local unpublished channel journal continuation

This is an unverified, isolated source candidate on
`cbattlegear-channel-queue-journal`, starting at
`99479711bfdb7c621765f09d671068ca8b8318ce`. It does not activate the production
graph, accept WP-208, publish a branch, or change the frozen #535/#537 ordering.
The Swift specification remains `db14559b39d32322b06477c6ae676112f583db50`.

The queue now carries the UUID assigned to the durable PendingSend in a private
entry, including during hydration. It does not reconstruct that identity from
the first row for a message. Null, DISPATCHING and UNCERTAIN submissions remain
visible and durable, with explicit diagnostics and no automatic wire dispatch,
query, FAILED event or shutdown status remapping. ACCEPTED is cleanup-only.
Neither SENT nor `isResend` is an acceptance receipt or proof of the intended
channel occupant. A saved origin and the original envelope must agree; the
current occupant is compared inside the actual dispatch fence, never copied
onto old text. No unbound history is hidden, deleted, rebound or migrated.

Each physical backoff attempt gets a fresh UUID and an exact
radio/pending/message/attempt key. The READY-only journal CAS and the actual
protocol operation run inside the injected connection lease's dispatch fence.
The fence owns operation/identity exclusion; the queue journal path does not
acquire a service-local mutex before that process operation lane. An absent
lease fails explicitly closed. Messaging never opens a lease, manufactures a
runtime admission or marks a slot reconciled.

Acceptance is settled inside the admitted operation, before cancellation can
escape its return. A lost settlement or completion response is reconciled by
reading the exact journal key, not by resetting or rearming a pending row.
Ambiguous protocol outcomes retain uncertainty. A raw DeviceError of any
code is not sufficient per-attempt definite-unsent proof at this boundary;
it settles UNCERTAIN before any backoff or channel query.
The protocol's explicit definitely-unsent cancellation disposition is not
interchanged with UNKNOWN. The storage transaction owns SENT-unless-DELIVERED,
the wire timestamp and resend counters/repeat reset once; the new queue path
does not repeat that bookkeeping.

Terminal retirement uses the independent
`QueuedChannelTerminalPersisting` role and the exact latest definitely-unsent
attempt. The producer transaction retires only that pending row and updates
FAILED atomically, rejecting a newer submission before either write. The
consumer publishes failure only from a returned changed-to-FAILED receipt,
deduplicated by its exact pending/message/attempt key rather than resampling
message-wide status, and never performs a later status write. A missing role, zero-attempt history,
guard rejection or lost terminal receipt is diagnosed, not fabricated as
successful retirement. The query accounting tests now suspend at this actual
atomic operation; their precommit status assertion is PENDING rather than the
old, unsafe FAILED-before-delete intermediate state.

### Counter-return loss across recreation

The per-queue `uncertainChannelCounts` marker is not durable proof. The actual
current flow is: the exact READY count transaction commits 0 to 1 without a
physical attempt; a lost/cancelled return leaves the durable submission READY
and blocks this queue instance; recreation drops that marker and a newly
invoked exact transaction commits 1 to 2. A fresh exact count receipt is still
followed by original-intent checks, the READY-only begin CAS and the actual
fence. The count readback is not used as wire authorization. This sequence
does not establish duplicate wire dispatch or prove a change of occupant.

It does change two decisions compared with a count-0 recreation control that
has not spent the first count:

- For `isResend`, `Attempt.preserveTimestamp` becomes true at 2 rather than
  false at 1. The first actual physical attempt therefore uses the saved
  timestamp instead of a fresh phone-clock timestamp. Ordinary non-resend
  submissions use the saved timestamp in either branch.
- The legacy channel-not-found disambiguation decision uses the post-bump
  drain count, not physical-attempt journal length. The initial draft's
  DeviceError(2)-to-DEFINITELY_UNSENT classification would have let count 2
  query and retire on absence after the first physical rejection, whereas
  count 1 would park below threshold. The safety follow-up below removes
  that classification: both controls now retain the exact UNCERTAIN attempt
  and pending pointer, with PENDING message status, no query, FAILED event
  or retirement. A spent drain count does not itself spend the thrown-query
  failure budget or certify a wire outcome.

Six authored recreation controls cover both persistence-error and
cancellation return loss, each comparing the saved-timestamp/first-wire and
uncertain-at-threshold paths with a no-lost-count control, plus replacement-occupant
fence rejection after recount. They preserve the same
pending UUID, prove no physical attempt precedes recreation, and assert one
actual physical attempt afterward only when identity admits it. The original
queue is signalled/hydrated again after loss to assert count remains 1 with
zero wire; successful successor controls assert count 2 and a fresh exact
pending/message attempt, its captured occupant and actual wire timestamp.
These are service-fake/recreated-queue
controls, not disk/process execution evidence; they have not been compiled or
run under the retained execution hold.

This is a demonstrated source-level consequence of counting drain admission,
not evidence that the increment ran twice within one drain or a newly
introduced defect relative to the legacy message-wide counter. Verified at the
unchanged Swift pin: `ChatSendQueueServiceAttemptCountTests.swift:145-167`
expects restart 1 to 2 with timestamp preservation (its harness exercises DM);
`ChatSendQueueService.swift:247-259,279-282` applies the same count/preservation
decision to channel resends. b5 confirmed that 902276 intentionally counts
drains and supplies no durable consumed-drain or selected-timestamp receipt.
Neither this source policy nor that disposition independently verifies the
new journal's first-physical-send behavior after a lost count return.
The coordinator explicitly selected retention of this pinned count-of-drains
parity, including restart recount and timestamp preservation, with no new
durable logical-drain/timestamp schema. Controls assert that selected policy,
not an unapproved physical-attempt-count reinterpretation. A scalar
count and empty physical journal cannot distinguish a lost return from a
returned count followed by a crash before begin. If the required invariant is
restart-stable logical retry/timestamp selection, storage needs an exact
pending-and-intent-bound recoverable drain receipt (stable operation identity,
post-count value and selected timestamp/preservation decision), with an
explicit atomic consume/advance transition distinguishing resume from the

## WP-215 pending-direct send-by-ID receipt follow-up

The local WP-208 successor based on `26742ecc2069dbfce8e30400014831f95f80e136`
extends receipt tracking to `sendPendingDirectMessage(messageID, contact, ...)`.
Each actual `retryLoop` wire call receives a fresh `MessageWriteDispatch`.
The first successful protocol return records ACCEPTED before claim bookkeeping,
ownership checks or ACK processing; ACCEPTED remains monotonic if an in-call
retry later fails. Only settled `DEFINITELY_UNSENT` cancellation or explicit
`DeviceError` restores READY. A newly invoked send rejects a non-READY receipt,
while internal ACK retries remain part of the already-owned call.

With a notification receipt, send failure/cancellation never changes the
pending row to FAILED. Existing in-call retries still set RETRYING and retain
their attempt bookkeeping; the receipt does not reset that state to PENDING.
A READY outcome clears only this operation's ACK
tracking; ACCEPTED/UNCERTAIN retains the row and its ACK tracking for late
correlation. Callers without a notification receipt retain the previous
failure behavior. This is in-memory outcome fencing, not durable delivery or
