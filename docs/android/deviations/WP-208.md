## Issues #524 / #514: separate creation and radio-acceptance observations

The bounded WP-208 producer repair integrates trusted main
`796a872a3565a66c74f782b738a9ecb3c273fb25`, which normally merged WP-107
PR #531's direct/channel dispatch-provenance API. The frozen source pin above
is unchanged.
WP-308 owns composer consumption; WP-215 owns notification handler/dispatcher
consumption; WP-302 owns navigation integration. Their consumer paths are not
edited here. WP-215's standalone `NotificationActionReceipt` prerequisite is
consumed from commit `bfd2418d99395e7302ff45dade2b67cba8611857`.

Pending creation now participates in the service's tracked session-owned work.
A caller can retain a single-use `PendingMessageCreation` context element around
either existing pending-create method. Its atomic snapshot records the allocated
DTO before the store write and COMMITTED immediately when the write returns,
before generation checks, contact bookkeeping or delivery through `await`.
On a thrown/cancelled save, one narrowly noncancellable exact-key store read
reconciles the settled write: matching DTO means COMMITTED; failed reads,
absence, or mismatched content mean UNKNOWN with the original identity retained.
The generic persistence port does not serialize that read against its original
insert, so absence cannot prove NOT_COMMITTED. That state requires an
owner-serialized store result and is not emitted by this path. The original
exception/cancellation still propagates. The read does not mutate a successor's
state or perform queue/radio work.
The receipt can also retain the exact DTO returned by a canonical
create-or-reconcile operation; it accepts COMMITTED only when the returned
radio/message ID matches the proposed row identity. The persistence contract
must validate the full immutable creation intent before returning that row.
NOT_STARTED means no save began; WRITING is not proof of commit. A receipt is
process memory, not a durable operation journal, and never authorizes blind
text restoration, overwrite of newer typing, enqueue or retransmission.

Inline notification sends carry WP-215's caller receipt into the session-owned
child without inheriting the caller job. After the initiating identity fence,
each actual direct/channel wire attempt gets a fresh WP-107 `MessageWriteDispatch`.
The receipt marks IN_FLIGHT immediately before the attempt and synchronously
records ACCEPTED on the protocol method's successful return. A definite device
rejection resets the receipt for existing pool backoff. On cancellation, only
the settled protocol dispatch owner's `DEFINITELY_UNSENT` disposition permits
reset to READY; UNKNOWN and MAY_HAVE_WRITTEN remain UNCERTAIN. Other wire
exceptions remain uncertain, never definite-unsent authority. The direct-send
postacceptance fence and ACK-info merge now sit outside the failure boundary,
so an observed acceptance cannot be converted to FAILED by those later failures.
Row creation, queue insertion, radio command acceptance and recipient delivery
remain distinct. Neither receipt claims exactly-once delivery or survives
process death. Existing signatures, no-receipt callers, queue/retry policies and
generation fences remain intact.

Trusted `reserve.py admit` accepts modify/create operations for the producer,
receipt, new `CommitRecoveryTest` and this document through `wp-owned`.
The automatic claim attempt reports the preserved historical WP-208
source/base/manifest/backend mismatch. The overlap report is advisory; the
coordinator assigned the producer exclusively, and WP-215/WP-302 confirmed no
competing producer edits. No reservation was released/recreated or edited by
hand. No native/Gradle owner or execution runtime was changed.

Authored, **not yet executed**: 32 supplemental dynamic cases (direct/channel
matrices) use the actual MessageService and MeshCoreSession, deterministic
RecordingStore barriers and narrowly delegated store/session roles. They cover
cancellation while queued on `pendingOperations` before the owned create body
allocates identity, before-write cancellation/failure, commit-before-return
cancellation/error, unknown reconciliation, single-use identity, generation
replacement, teardown, observed acceptance before caller cancellation/teardown,
unobserved wire reply and definite device rejection. The dispatch-specific
cancellation cases hold the real session serializer: cancellation while queued
proves no matching transport write and permits one retry after release;
cancellation after the matching write is recorded remains UNCERTAIN and cannot
authorize replay. These are not Room transaction evidence;
WP-308/WP-215 downstream real-store integration remains separately owned.

## WP-215 pending-direct send-by-ID receipt follow-up

The local WP-208 successor based on `26742ecc2069dbfce8e30400014831f95f80e136`
extends receipt tracking to `sendPendingDirectMessage(messageID, contact, ...)`.
Each actual `retryLoop` wire call receives a fresh `MessageWriteDispatch`.
The first successful protocol return records ACCEPTED before claim bookkeeping,
ownership checks or ACK processing; ACCEPTED remains monotonic if an in-call
retry later fails. Only settled `DEFINITELY_UNSENT` cancellation or explicit
`DeviceError` restores READY. A newly invoked send rejects a non-READY receipt,
while internal ACK retries remain part of the already-owned call.

With a notification receipt, send failure/cancellation never changes the
pending row to FAILED. Existing in-call retries still set RETRYING and retain
their attempt bookkeeping; the receipt does not reset that state to PENDING.
A READY outcome clears only this operation's ACK
tracking; ACCEPTED/UNCERTAIN retains the row and its ACK tracking for late
correlation. Callers without a notification receipt retain the previous
failure behavior. This is in-memory outcome fencing, not durable delivery or
exactly-once evidence.

Independent review identified that inline channel sends lacked the top-level
fresh-action guard already used by direct sends. The guard now runs before
allocating or saving a new channel row. Shared direct/channel acceptance and
uncertainty cases explicitly retry the same retained receipt and assert the
typed failure, unchanged receipt state, one stored row and one wire attempt.
This rejects a new logical action, not an already-owned internal retry.

An independent exact-head review of `9ab34b0f183390fdfdef28f531ea9c7ca32e5566`
against base `1c8ad47463bbff68a67132f05ce6f33d423ed83a` found that concurrent
top-level calls could both observe READY before either reached `notificationWire`.
The repair claims the receipt under a process-local registry lock before entering the
session-owned operation (and before the channel-operation mutex), allocation,
or persistence. The claim is separate from wire state: it leaves the receipt
READY until a real attempt starts, rejects an overlapping caller before it can
create a second row, and is released in `finally` only after the owner operation
settles, including calls routed through different `MessageService` instances.
A single owner retains the claim through explicit DeviceError
pool-backoff retries; a new action may claim again only after that operation
returns and the receipt remains READY. This covers inline direct/channel and
queued direct operations without changing the WP-215 receipt contract.

The new direct/channel race controls hold the first store save before commit,
advance the deterministic clock by one second, and start a second call with
the same receipt. They require the second call to be rejected while the first
is still held, with no row or wire attempt and the receipt still READY; after
release, the first call succeeds with one stored row and one wire attempt.
Direct/channel controls repeat the overlap through separate service instances.
Additional direct/channel controls require the same top-level owner to complete
an explicit DeviceError backoff retry, proving the claim does not block
legitimate internal retries.

The same schedule exposed a separate cleanup gap: a definitely-unsent inline
cancellation returned the receipt to READY and removed ACK tracking, but left
the already-saved row PENDING without a pending-send queue entry. READY failures
for newly-created inline sends now complete the existing owner-fenced FAILED
transition under the per-message mutation lock, including pre-wire cancellation
and explicit DeviceError. The existing queued-direct `notify=false` path still
retains its PENDING row for same-row retry, while ACCEPTED and UNCERTAIN inline
outcomes remain untouched. Deterministic direct/channel controls assert FAILED
for definitely-unsent rows and PENDING for possible-wire cancellation, then
verify that a later READY retry does not leave an orphaned PENDING row.

## Bounded queue-query progress repair (WP-501 issue #261)

The frozen queue keeps a per-envelope consecutive query-failure counter, with
disambiguation after three send attempts and a default cap of sixteen actual
query throws. Android's per-connection graph replacement discards that counter
after a real query timeout fences the session. Retrying on a fenced session is
not another query failure and is not evidence that the channel is absent.

`ChatSendQueueProgress` is an Android process-lifetime adaptation, explicitly
injected into replacement queues. It retains only counters, partitioned by
radio/message identity and bound to the persisted pending-row UUID. All drains,
subscriptions, ACK waiters, transports and services remain connection-owned.
Attaching a newer generation fences all older progress leases. Retiring a lease
does not erase pending counters; successful hydration prunes deleted/replaced
rows for that radio. Genuine query success resets the counter, including a real
null result; successful send/terminal deletion also clears it. Terminal storage
failure retains progress so reconnect does not restore a full retry budget.
Cancellation and stale ownership checks are not query failures.

The optional constructor argument preserves existing callers' historical local
lifetime. It is NOT the App fix. WP-303 must retain a single owner in AppContainer,
pass it through SessionEnvironment (including withLifecycle reconstruction), and
inject it into every ChatSendQueueService. No App, database/schema, runtime,
protocol fence or shared WP-501 fixture is changed here. WP-207 separately owns
physical recovery after CorrelationUncertain. Whole-bug acceptance requires both
actual consumers and fresh WP-501 App-edge execution.
In particular, the protocol emits uncertainty before the caller necessarily
observes its query failure; Default-dispatched runtime recovery may retire the
queue first. The queue's concrete `suspend fun awaitChannelQueryAccounting()`
now seals further send/query admissions and observes its actual
generation/message/pending-row-bound query through
genuine outcome accounting and pending-status park or terminal persistence.
WP-207 must await it, through WP-303's actual graph delegation, before token
withdrawal, scope cancellation, lease retirement and physical teardown.
Manual stop/replacement cancels the observation; observer cancellation does
not cancel the query or reopen admission. Both drains stop after the admitted
envelope, not by cancelling it. Durable enqueues remain pending for the next
graph. The barrier is not a drain join, grace delay, failure
counter or default-success graph hook. Source ChannelService retry timing and
the correlation fence are unchanged. Nine new deterministic cases include
early recovery inside the actual ChannelService retry window and blocked
terminal deletion while the token remains current, exact B attempt-count
preservation before recovery resumes, idle preparation followed by competing
direct/channel enqueues, and preparation during suspended preflight.
The real App edge must still prove that the actual consumers adopt this
ordering. A correlation diagnostic/cancellation is not substituted for a query
failure, and lower-level tests do not establish complete App acceptance.

Sixteen supplemental deterministic cases exercise the concrete MessageService,
MeshCoreSession and raw firmware transport with RecordingStore. They include the
default sixteen genuine timeout threshold across sixteen session replacements,
the unchanged 1,999/2,000ms query observation window, same-channel envelope B
survival after A fails, reset/cleanup, pending-row identity, radio isolation,
cancellation, storage failure and non-cooperative late query completions.
RecordingStore is not Room/device/process-death compatibility evidence. Tests
are authored, not passing evidence until actual runner discovery/execution.
See `docs/android/evidence/WP-208/queue-recovery-accounting.md` for exact outcomes
and the truthful advisory-reservation/local-readiness limitations.

independent WP-501 source review: typed Failure logs occur before persistence,

## ACK retained across inline failure cleanup

Exact-head review of `9343780c3a0c5626043c10ad254b60f6efa7214d` identified an
ACK registration interleaving with inline definitely-unsent cleanup: cleanup
could remove pending ACK tracking after the handler recorded the ACK but before
the failed-status write completed. The same lock/write ordering existed in ACK
expiry and fail-all cleanup. All three paths now persist the failure before
retiring tracking, then atomically check for an ACK under the same tracking
lock. If one arrived during the write, they retain the ACK and restore the row
to SENT so the serialized ACK reconciler can commit DELIVERED. ACK reconciliation
restores a FAILED row only when an in-memory marker binds that exact ACK
