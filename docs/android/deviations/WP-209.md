# WP-209 native contacts, channels and advertisement adaptations

Reference: `db14559b39d32322b06477c6ae676112f583db50`.
Owner: `services-porter`. **External contribution:** this was prepared outside the
dispatch controller, with no lease, session or receipt. These are proposed
adaptations for coordinator review. All code is pure JVM in
`core/services/.../services/contacts/`. `RepeaterResolvable` and
`AdvertLocationPolicy` reuse their existing `core:model` implementations.

## A-01: shared shape

Confined state and an injected `CoroutineScope` replace actors. Clocks, sleep,
jitter and logging sinks are injected, and logging is a no-op by default, because
`PersistentLogger` lives in WP-212. `deinit` becomes cancelling the scope.
Cancellation is never swallowed: wherever Swift's `try?` or a catch-all would
absorb it, Kotlin rethrows. The exceptions are the places Swift itself can't be
interrupted, namely a round after it fires, event handling, `stopEventMonitoring`
and clearing the manual-sync flag, which run non-cancellably.

Counts are `Long`, following the existing contracts, and out-of-range timestamp
conversions throw or wrap where Swift would trap. Each service takes a narrow
session role (`ContactSessionOps`, `ChannelSessionOps`, plus advertising and
event-source roles) instead of the whole session protocol.

Event streams use small lock-confined broadcasters with single-consumer
subscriptions that register immediately. `core:runtime`'s `EventBroadcaster`
can't be a dependency here.

## A-02: ContactService

By-id methods take `EntityKey` (radio + id) because the Kotlin persistence
contract requires the radio for every by-id lookup. Collaborators that aren't on
`main` are reached through `ContactServicePorts.kt`: SyncCoordinator,
NotificationService, RemoteNodeService and a `UserDefaults`-style flag store.

These match Foundation:
- share-token parsing (graphemes, the ICU `\d` match with an ASCII-only integer parse);
- whitespace trimming (`whitespacesAndNewlines`);
- `URLComponents` query encoding (`+` becomes `%2B`).

### Atomic contact avatar persistence repair

The pinned Swift avatar method fetches a complete DTO and saves its avatar-modified
copy. Android instead passes the fetched public key and `EntityKey` to an
existing-row-only repository operation. Room checks the current scoped row and
full public key inside the write transaction, then updates only `avatarImageData`
with SQL `UPDATE`, including `null` to clear. It never upserts. Missing rows and
different-key replacements return distinct typed outcomes; the service maps both
to its existing `ContactNotFound` error and notifies contacts only after success.
Storage errors and cancellation propagate unchanged. `RoomPersistenceStore`
exposes the operation through its existing `ContactPersisting by contacts`
delegation. No schema or backup-format change is required.

For the WP-311 chooser consumer, the explicit
`ContactService.updateContactAvatar(contact, expectedPublicKey, imageData)`
overload accepts the identity captured before asynchronous selection. It does
not re-query and substitute a new identity at commit. The existing two-argument
`EntityKey` overload remains compatible with current-main callers.

This protects unrelated metadata committed before the avatar transaction,
deletion after the caller fetch, and different-public-key replacement at the
same radio/id. It does **not** detect delete/recreate with identical
radio/id/publicKey: there is no persisted incarnation or no-reuse invariant.

`ContactAvatarRoomTest` exercises set/clear, independent-repository metadata
commits, deletion, key replacement, and same-ID/same-key foreign-radio controls.
Service native cases exercise typed outcomes, no full-DTO save, success-only
notification, missing initial fetch, storage failure and cancellation.

The coupled favorite acknowledgement path also uses an existing-row,
full-identity-checked transaction. It changes only `isFavorite` and flags bit 0,
preserving all other current flag bits and fields. In particular, a favorite
request held at radio acknowledgement cannot restore its fetched avatar over
a concurrent avatar set/clear. Missing/replaced contacts map to the existing
`ContactNotFound` service error after acknowledgement; storage/cancellation
behavior remains unchanged. This narrowly replaces the source's full-DTO
post-ack save; unrelated metadata, including a nullable last-heard value, is
no longer rebuilt by a favorite-only mutation.

Four additional actual-Room methods exercise held-ack favorite on/off against
avatar set/clear, concurrent nickname/unread/non-favorite-flag changes, foreign
radio isolation, delete/replacement, cancellation, and typed store outcomes.
Two native service cases assert acknowledgement-before-write, no full-DTO save,
typed outcomes and unchanged persistence/cancellation failures.

## A-03: ChannelService, flood scope and hashtags

`RxLogService.updateChannels` is reached through `ChannelDecryptionCache`.
BLE transport errors go through an injected classifier, because the BLE
exception type lives in a module `core:services` can't depend on. Until that's
wired, BLE send failures count as `Unknown`. `NSDataDetector` has no JVM
equivalent, so hashtag link exclusion recognises `http(s)://` and `www.` only,
and bare domains are not treated as links. Ranges are inclusive UTF-16
`IntRange`s, and lowercasing uses `Locale.ROOT`.

**Protocol behaviour that limits two source recovery paths, for coordinator review:**
- After a `getChannel` timeout or an unanswered pipelined read, the Kotlin session quarantines that read family on the connection and throws `ConnectionLost` on later reads. So `fetchChannel`'s timeout retry surfaces as `Unknown` rather than a retryable `Timeout`, and reconciling dropped pipeline reads can't recover on the same connection.
- The protocol's `getChannel` ignores device `ERROR` replies, so a NOT_FOUND reaches the service as a timeout.

This historical same-connection behavior is superseded for pipeline recovery by
the approved R118 policy below; the protocol quarantine is not relaxed.

### Issue #380: composed fresh-session recovery (WP-209 with WP-207 support)

The approved G01/CM-01 decision in `WP-107.md` requires physical teardown and a
fresh handshake, not another same-link read. ChannelService now commits the
received configured/empty slots and reports every missing slot as a non-retryable
transport error requiring a fresh connection. Unread rows remain untouched. That
per-connection service refuses subsequent reads/retries rather than entering the
quarantined session; the replacement graph owns the recovery read.

`RadioSessionContainer.awaitChannelQueryAccounting` joins the active channel
sync's persistence/cache/notification tail before the existing WP-207 correlation
recovery tears down the graph. Entering that barrier retires channel reads on
the current service, including serial timeout retries and later serial slots;
every fetch attempt checks retirement after any retry delay.
The accounting handoff carries the controller's actual typed correlation failure.
An already-admitted fetch in timeout backoff reports that same cause without
calling the protocol again; new fetches remain rejected. This preserves the
pending-message queue's genuine query accounting rather than replacing its
originating failure with a generic disconnection.
Completion/cancellation releases the barrier in
`finally`; manual disconnect still cancels work rather than forcing a commit.
The controller clears channel skip timestamps only for the current recovering
generation so the fresh graph cannot mistake the partial attempt for a reason
to omit channel recovery. Existing physical ownership, teardown receipts,
reconnect policy, generation checks and protocol quarantine remain authoritative.
Correlation recovery also stands down when the originating connection operation
is cancelled; caller cancellation must not race the accounting barrier into a
new automatic connection.

The four source pipeline recovery scenarios retain their original case IDs but
assert this approved native outcome instead of scripted same-link success or a
local retry breaker. `ChannelRecoveryIntegrationTest` exercises the actual App
factory, MeshCoreSession, controller and Room boundary with a protocol-speaking
radio role. It covers commit-before-close, fresh appStart and successful recovery,
late old callbacks/frames, cancellation/manual stop and failed fresh connection.
These are simulated-transport integration cases, not physical-radio acceptance.
The serial-stall companion uses actual non-pipelined reads and proves that
neither the timed-out index nor a later unread slot reaches the old transport.
See `../evidence/WP-209/composed-session-recovery.md` for execution status.

## A-04: AdvertisementService and delta sync

Debounce, minimum interval and busy backoff use the injected clock. After a
round fires it can't be cancelled, except inside the delta-sync handler. A
cancellation of the round itself follows the source's cancelled-round path. Any
other exception counts as a failed round, because Swift handlers can't throw.
That includes a cancellation the handler raises while the round is still live,
such as an internal timeout. A round cancelled before it starts still clears its
registration. Two actor segments stay atomic under the lock. The deletion
flush's final empty check, or its failure requeue, releases the flush in the
same section. A restarted event monitor cancels its predecessor before the new
one starts. Errors are a sealed
`AdvertisementError`. `advertContactFrame` is the advert-local name for the
frame conversion. One log line prints the contact type as `CHAT`, not `chat`.

## A-05: neutral fault carrier (`external-WP209-neutral-fault-amendment`)

The maintainer approved this seam on PR #49. This PR is the only writer of
`android/core/contracts/src/main/kotlin/com/meshcoreone/android/core/contracts/domain/errors/ContactsChannelAdvertisementFaults.kt`
(package `com.meshcoreone.android.core.contracts.domain.errors`). The file is pure
JVM and declares:

- `SourceServiceFaultCarrier`, an interface with one member, `val sourceServiceFault: SourceServiceFault`.
- `SourceServiceFault`, the sealed root of every family.
- `ContactServiceFault`, `ChannelServiceFault` and `AdvertisementFault`, one sealed sub-interface per family. Each enumerates its Swift enum's cases one-for-one.

Cases without a payload are `data object`s. Cases with a payload are `data class`es
with `val` fields. The payloads are the exact raw values: the Channel `reason`
strings, `consecutiveFailures`, and for every `SessionError` the producer's
identical `MeshCoreException` instance (not a copy or a string). The file has no
string tags, `Any`, reflection, display copy, UI/data/runtime types or policy.

`SourceServiceFault` is sealed by package and module, not by file. PR #50 can
therefore add its RemoteNode, RoomServer, BinaryProtocol and NodeConfig families
in the sibling file `RemoteRoomNodeConfigFaults.kt` without touching this one. A
throwaway sibling family compiled locally, appeared in `SourceServiceFault`'s
`PermittedSubclasses`, and a `when` that omitted it failed to compile. The file was
then deleted.

The three producers keep their names, constructors, messages, `errorDescription`,
`toString`, raw fields, causes and caller/retry behaviour. Each one implements the
carrier with a covariant getter: an exhaustive `when` over its own sealed class,
with no `else` branch. Adding a producer case without a payload case is a compile
error. The projection lives in the producer. No UI or service code constructs the
payload.

## Test adaptations

- **Sync coordinator stand-in.** The three manual-refresh sync cases run against a fake that implements the source advert-claim protocol. Re-run them once the real `SyncCoordinator` (WP-214) lands.

## Issue #517: contact writes outliving a confirmation

The Swift add/update sequence awaits the radio, saves the frame and notifies the
coordinator. Kotlin's independently owned request serializer previously retained
a sent exchange after UI cancellation but not that service tail. The contact
operation now installs a suspend completion inside that same response owner.
Only accepted writes enter its narrowly non-cancellable persistence/refresh tail;
queued cancellation still prevents dispatch and caller cancellation still
propagates. No UI navigation or delivery acknowledgement runs in the completion.
The existing wire packet, error matcher, timeout and ambiguous-reply quarantine
are unchanged.

The Room upsert compares the current row inside its write transaction. A greater
`lastModified`, or an equal-timestamp frame changed since the initiating read,
cannot be overwritten by an older completion. An intentional equal-timestamp
update of the observed frame remains supported; preferences, identity, activity
and unrelated-radio rows remain intact. Retaining a newer frame is an explicit
non-save outcome: the service reports `ContactWriteCompletionFailed` and requires
reconciliation instead of reporting that the imported frame was saved.
Failed durable recovery recording is reported without replacing cancellation;
the process retains the recovery epoch, retrying pending true-marker recording on
guarded access. This cannot promise persistence across process death when disk
writes fail.

Potentially sent cancellation, unknown results and failed local accounting set a
durable per-radio recovery flag. A marked epoch rejects subsequent full and
incremental sync before fetching or persisting any snapshot. There is no
production caller of the internal `reconciled` helper and no automatic clear,
even for a complete equal-count snapshot. A future guarded reconciliation
contract must supply genuine protocol drain/ordering authority spanning the
destructive persistence transaction and matching marker update. Ordinary clean
sync retains its snapshot-application fence and invalidates queued writes so
they cannot pass the dispatch boundary after that snapshot.

An unacknowledged `MAY_HAVE_WRITTEN` exchange cannot be retired by a full snapshot,
session teardown, reconnect or READY state: this implementation has no
cross-session physical-drain receipt. The per-radio recovery marker therefore
remains set and writes remain blocked until a future producer supplies genuine
drain evidence. Likewise, a persisted marker loaded without its in-memory
dispatch provenance is fail-closed and has no automatic recovery path today;
this is an explicit limitation, not permission to reset the marker. The Android
flag adapter uses checked synchronous commits; recording errors remain attached
to the originating exception, preserving cancellation rather than manufacturing
success.

`ContactWriteCompletionFailed` distinguishes confirmed radio acceptance from a
failed local save/refresh. `needsContactWriteReconciliation(radioId)` exposes the
persistent recovery requirement. Even a late accepted write that was saved can
conservatively retain that requirement; a later ordinary sync cannot clear it.
A dismissed UI must
not interpret cancellation as rollback and must reread persistent state on
re-entry. Mounted confirmation integration remains WP-302-owned; this repair
does not import or modify its unmerged UI.

See [the repair scope and verification boundary](../evidence/WP-209/contact-write-recovery.md).
