# WP-214 sync coordinator and sync retry adaptations

Reference: `db14559b39d32322b06477c6ae676112f583db50`. Base: `main` @ `7237727f`.
**External contribution:** prepared outside the dispatch controller, with no lease,
session or receipt. These are proposed adaptations for coordinator review. The sync

## Classified native channel reaction failures (issue #613, bounded follow-up)

The pinned Swift `SyncCoordinator+ReactionHandlers.swift` uses `try?` for the
native target read, treats a nil persistence result as a saved reaction, and
discards the pending matches returned when indexing a DB-found target.
Android distinguishes a genuine target miss from a failed read. Classified
native work is now admitted durably before target lookup; a confirmed miss or
failed read retains the original work. Legacy misses remain session-owned.
A known target uses the same serialized persistence/reconciliation
consumer as indexed replay, including the notification obligation established
before an uncertain save. A DB-found target is indexed through the persisting
consumer, never a drain whose returned work is discarded.
Channel history indexing also uses `reactionTimestamp` (the preserved sender
stamp), matching direct history, rather than a corrected display timestamp;
otherwise a retained reaction's original hash cannot find its stored target.

For classified native channel reactions, an interrupted save or summary update
is now retained as an unknown mutation outcome, rather than retried after a
negative tuple-existence read. A save is reconciled only after reading the exact
committed occurrence and original target incarnation. Without per-operation
summary evidence an uncertain summary update remains pending: even an equal
summary cannot prove which update committed. Without proof the
entry and later matches for that incarnation remain pending in order; a
separately proven replacement incarnation can still receive its own reactions.
This can leave work unresolved even when a write did not commit, because absence
is not evidence that an uncertain write cannot still commit. Direct and legacy
reaction behavior is unchanged.

Android Room now offers an optional `ReactionSummaryReceipting` authority for
classified native channel reactions with a proven target incarnation. The
original occurrence ID identifies one immutable summary request. Updating the
summary and inserting its receipt share a single Room transaction; failure to
store the receipt rolls back the summary too. Reusing an operation ID with
different arguments is a typed identity conflict. Repeating an exact request
never rewinds a later summary. Reading its receipt validates the original radio,
message incarnation and current channel occupant in the same transaction, and
returns the current stored target rather than restoring an old summary value.

The existing real native replay/reconnect consumer can therefore complete an
unknown summary response from exact operation proof, without issuing the update
again. It preserves the original notification obligation, including no new
obligation for a duplicate reaction, and then consumes later pending work in
order. A missing receipt, equal value, changed target, or a store without this
optional capability does not prove success or authorize retry. Receipt read
failures are reported as fresh failures and restore the pending work; cancellation
propagates. Unknown saves still require their separate committed-occurrence proof.
Direct and legacy reaction mutation paths are unchanged.

The schema-8 step added only local summary-operation evidence, not pending custody.
The 7-to-8 migration invents no proof for historical summaries. Receipts remain
local children of their target message, are deleted with it, and are not exported
in the iOS-compatible backup envelope. `ReactionSummaryReceiptTest` covers actual
SQLite rollback, immutable operation identity, later-value protection, radio and
incarnation fences, deletion and file-backed reopen. `IncomingReactionSummaryReceiptTest`
drives polling, the real graph, Room and reconnect through lost responses,
post-commit cancellation, receipt-read failure, a rolled-back summary followed by
an equal legacy update, duplicate notification policy and target replacement.

### Durable classified custody (schema 9)

Room now also stores classified native channel work, independently of target
deletion. The original occurrence, radio/channel, parsed/raw text, sender,
nanosecond receive time, local-name and delivery snapshots, key/entry ordinals,
target incarnation, notification obligation and in-flight phase survive reopen.
The original three file-backed restart regressions from
`cbattlegear-reaction-restart` at `5782b90f` are included with their original
assertions; only a function reference changes to await the now-suspending requeue.

Channel custody transitions await a conditional Room transaction before changing
the memory image. The same transition removes native victims of the existing
shared native/legacy oldest-key/oldest-entry eviction policy, and removes completed
work. Legacy entries still share the 100-entry channel cap and retain their old
session ownership; the independent DM queue is unchanged. Taken native work is
retained separately until completion, rather than losing custody during the drain.
Restored in-flight work keeps its original priority and binding. A stale requeue
cannot re-admit completed or evicted native work. Capacity eviction is logged;
durable retained custody additionally rejects more than 200 records with a typed
capacity error instead of silently dropping in-flight work.
Serialized consumers also retain taken legacy work in session-owned memory until
completion or successful requeue, so failed native reconciliation cannot discard
the rest of a mixed batch. This does not make legacy work restart-durable.

Each snapshot has an immutable transition identity and conditional predecessor.
If a transition's response is lost, the next operation first reads exact committed
state: it adopts the matching candidate, proves the old image unchanged, or fails
explicitly. It never writes a stale memory image over a committed eviction or
completion. Storage errors propagate; a failed replacement rolls back admission
and eviction together. An empty terminal snapshot retains its transition identity.
History can reacquire abandoned in-flight work under the shared persistence mutex
without requiring another connection. Session teardown removes only session-owned
memory work, including from an unconfirmed candidate, without needing storage access.
The 8-to-9 migration creates empty custody, never historical classified work.
These records are local process state, not backup-envelope additions.
Device-data deletion purges that radio's journal in the same transaction and
advances the transition identity. Post-commit invalidation reconciles and revokes
matching memory/unconfirmed custody without restoring deleted work or discarding
other radios. A rolled-back deletion does not publish invalidation.
Its exact predecessor identity distinguishes committed from uncommitted admission
even when purging the radio erases the changed rows; equal filtered snapshots do
not authorize resurrecting a legacy eviction victim.

Native durable selection now reads the target and stores its binding under one
Room transaction and queue predecessor check. Cache witnesses are provisional and
consulted inside that transaction; the normal bounded database lookup shares the
existing candidate ordering, text/hash, original local-name and receive-window
rules. Admission is durable before selection starts. A crash before transaction
commit leaves ready work, not an ambiguous selection marker; a committed selection
retains its exact original target/incarnation even if the response is lost.
The operation's immutable transition identity proves that result on reconciliation;
all other occurrence/context/order/phase fields must still match. No reaction
mutation or notification is issued before binding acknowledgement.

Save and summary phases are written ahead of their corresponding operation.
Once bound, a target never adopts a replacement's incarnation.
Unknown saves still need exact committed-occurrence evidence; unknown summaries
still need the atomic operation receipt from schema 8. Missing proof remains
retained, not retried. A known save completion durably preserves its notification
obligation before summary work; summary uncertainty is retained until proven
completion/removal. Event publication is not a platform-delivery acknowledgement.

Historical `Binding` markers from the pre-atomic implementation remain a deliberate
conservative limit. Their original selection result was never stored, so recovery
cannot know which incarnation was selected and retains them visibly without
re-running lookup or binding to history. They cannot be upgraded by assuming that
the new transaction also protected an old read. New durable incoming and reconnect
selection does not create these markers. `DurableReactionQueueTest` covers atomic
binding rollback, live and reconnect response loss, original-incarnation fences,
and rejection of changed receive context, while retaining the historical-marker
quarantine control. Existing real Room target-read fault fixtures now intercept
the atomic selection boundary, without changing their recovery assertions.
Session teardown stops polling consumers before clearing session reaction custody:
a suspended selection owns the queue mutex until its consumer is cancelled.
`DurableReactionQueueTest`
also checks confirmed lookup cancellation with a lost checkpoint response,
cancellation before the persistence lock with an already-selected target, unbound
in-flight history recovery, mixed-batch storage failure and device-data deletion.
It checks this quarantine, grouped order/context/radio isolation, taken-work restart,
replacement fences, committed/uncommitted unknown saves, completion rollback/lost
responses, admission/take response loss, stale writers and shared legacy
eviction. `IncomingReactionRestartCustodyTest` closes and recreates the real
store/AppContainer graphs for the original target/existence/unknown-summary cases.
No pre-classification, actual process-kill/device, or notification-delivery
guarantee is established by these file-backed JVM controls.

Timeline preparation distinguishes retained unknown outcomes from a new replay
failure. Already stored messages remain displayable during open/refresh without
retrying or acknowledging the retained mutation; only proven completed results
replace their stored summaries. New storage failures still surface as failures.
`IncomingReactionRoomFailureTest` covers repeated preparation of the original
target before and after a late summary commit, and while a save remains unknown.

After a usable connection sync, Android makes a bounded recovery pass over
that radio's process-retained classified native channel reactions. Unlike Swift's
session queue, this receiving consumer does not require opening history or
receiving another reaction. Unselected targets are looked up with the retained
receive window and local-name policy; selected targets retain their original
incarnation. Work stays in original queue order, read failures and cancellation
restore custody, uncertain saves require the same committed-occurrence proof,
and uncertain summaries are never retried. Durable native target misses are now
included; DM/legacy queues and other radios are not drained. One connection-owned
loop now repeats that bounded, serialized pass 30 seconds after the previous pass
finishes, so later transient failures can recover while the same connection stays
usable. This bounds the rate, batch and concurrency, not the total number of
verification passes during a long connection. It is not a deadline or delivery
guarantee. Empty loaded custody does not cause a storage mutation. Identity import
cancels and joins recovery, including passes waiting for the persistence mutex,
before proceeding with the hardware handoff. An unchanged identity resumes
recovery only if this graph previously reached usable sync; a changed identity
does not restart the old graph's recovery. Actual failures remain logged by the receiving
consumer. Missing mutation proof and historical `Binding` quarantine remain
retained, not silently retried as new mutations.
The loop and each pass are children of the connection graph, outside the sync readiness
barrier: an old screen holding the shared persistence mutex cannot block a
healthy replacement from becoming ready. Sync reset and retirement cancel and join the loop and pass
before finishing event streams or clearing session queues.

`IncomingReactionRoomFailureTest` covers actual Room target/existence failures
recovering on reconnect without history, the original receive window after time
advances, cancellation during the recovery lookup, and an uncommitted uncertain
save that remains untried while later work stays ordered. Cancelling a later
lookup preserves already-resolved target bindings, so a subsequent retry cannot
attach the earlier occurrence to a replacement incarnation. Existing mounted
recovery controls cover committed saves, unresolved summaries and notification
publication across replacement graphs.
The active-connection controls exercise actual Room target/existence read faults
without reconnect/history, original receive context after the clock advances,
replacement-incarnation rejection, cancellation after a failed paced pass, and
multiple unknown-save proof checks that preserve later work until an exact late
commit is available. These are JVM service/Room controls, not radio or Android
background-execution evidence. Identity-import controls hold that shared mutex
through the actual import-start callback, release it during the private-key
exchange, and verify that custody remains untouched until an unchanged graph
resumes. A changed-identity control retains custody without restarting the old
graph while UI handoff completion is held.

The retained native channel entry carries the parsed reaction, exact original
text, sender, radio/channel, receive time, local-node-name snapshot and
`DeliveryContext`. Recovery uses the existing history/incoming/outgoing target
indexers and exact target binding from WP-307. It neither invents a new target
identity nor overwrites the original receive time with a later service clock.

Ordinary native candidates now enter a separate process-owned receive holder
synchronously when the poller selects the original parsed message for dispatch,
before metadata I/O or its receiving consumer can suspend. The holder preserves
that object, radio/channel index, receive time, local name, delivery context and
occurrence ID. Native reaction handling does not use a channel DTO, so this path
skips Swift's earlier, best-effort channel metadata lookup rather than treating
a failed lookup as absence. Metadata failure cannot strand a native receive
before its ordinary handler. Compatibility adapters that already resolved
metadata still admit before their receiving consumer runs.
Pure native-text recognition is not target selection or origin authorization.
Meshcore-open, DM, non-reaction and legacy polling paths retain their previous
behavior, including their metadata lookup; the opt-in/guarded receive path is
not activated.
Distinct equal delivered objects remain distinct, while weak identity witnesses
prevent redelivery of the same completed source object from readmitting work.

Unlike Swift's best-effort read fallbacks, a native candidate with this custody
waits for successful RX and duplicate reads. A confirmed duplicate is consumed
before its optional repeat-path mutation, so an uncertain repeat write is not
replayed. Original-radio receives are retried in order by the existing
connection-owned recovery pass. A native journal write marks a transfer in
progress; only its successful return or exact committed transition proof removes
the early holder. An exact unchanged preimage returns it for retry with the same
occurrence ID. Per-worker ownership fences release and transfer, so a late
`finally` cannot reset a newer consumer admitted by journal rollback proof.
`IncomingChannelReactionCustodyTest` deterministically interleaves those two
workers through the actual native queue's unchanged-preimage reconciliation.
An unproved write stays quarantined, not treated as unattempted.
These callbacks use the existing journal reconciliation and do not infer success
from an equal queue image. Confirmed admission removes early custody before
selection/save/summary, leaving the existing mutation and eviction protections
authoritative.

The early holder admits at most 100 active receives process-wide and rejects
overflow explicitly through the real polling consumer; it does not evict already
accepted work. This is separate from the unchanged classified native/legacy
queue capacity and eviction policy. Radio-data deletion removes early custody.
An overflowing delivery remains parked in its original poller: an explicit poll
can retry it after accepted work drains, but retiring that poller still does not
give rejected work process custody. The bound and explicit failure requirement
do not establish lossless overflow or a firmware redelivery policy.
`IncomingReactionReceiveCustodyTest` exercises actual Room read faults, retirement
on both sides of classification, equal occurrences, the capacity boundary,
proven/unknown admission outcomes, duplicate handling and the non-reaction save
control through real connection graphs. Its pre-handler control bypasses an
unavailable, unused channel lookup, then retires during the first actual native
read and verifies the original receive after replacement. A non-reaction control
still encounters the actual Room metadata failure and requires its original
poller to retry. `NativeMessagingTest` cancels a real poller synchronously after
source acceptance but before its suspending consumer starts, and checks handler
replacement/clearing does not retain an obsolete early callback.

This is a process-lifetime increment, not pre-classification restart durability.
There is still no guarantee before the poller selects a delivery for dispatch
(including radio dequeue/acquisition or event coalescing), for
work rejected at capacity, across a process kill before classified admission, or
for platform notification delivery. No guarded-origin proof is invented.
Known-target live retries consume earlier retained entries under the shared
mutex, in queue order, before the new occurrence. Repeated failed saves retain
the original occurrence and one notification obligation instead of giving each
retry its own obligation or replacing its receive metadata. Resolved channel
entries match their exact target within the original radio/channel even after a
local-node rename; unresolved entries still require their original sender/hash.
An incomplete persistence result is not logged as saved, including the shared
legacy helper's nil-result branch.

`IncomingChannelReactionRecoveryTest` drives actual polling, sync, Room,
session teardown/replacement and the mounted history consumer. Its cases
distinguish a miss, failed/cancelled target reads, failed existence reads,
save failure before/after commit, cancellation after commit, and summary
failure before/after commit. Recovery checks one stored reaction, the original
receive context and one publication without repeating a committed save.
Advancing-clock live retry, repeated arrivals and outgoing-target
rename controls exercise original-occurrence and notification ownership.
Existing `IncomingReactionSyncTest`, `ReactionServiceBehaviorTest` and history
replay tests remain controls for ordinary/legacy and outgoing behavior.
`IncomingReactionRoomFailureTest` exercises actual Room target/existence read
failures, a late save commit, unresolved summary updates, and replacement-target
isolation through the live sync and indexed replay paths.

This is **not a firmware-acquisition guarantee**: early custody starts at the
poller's synchronous dispatch selection, not firmware dequeue or event coalescing, and is
not restart-durable before classified admission. The original parsed object is
retained, not a proven firmware-origin envelope. The paced trigger only runs while a usable connection
graph remains alive; it is not a process-wide/background worker or a firmware
redelivery policy. General intake/retirement policy is unchanged. Historical interrupted selection and unproved
mutation outcomes can remain unresolved across restart.
The existing bounded queue's eviction policy is not made lossless. Successful
event publication still does not prove a platform notification was delivered.

## Receive-clock range recovery (issue #392)

The maintainer decision recorded on #392 at
https://github.com/cbattlegear/MeshCoreOne-Android/issues/392#issuecomment-6460375543
supersedes the previous timestamp-range HOLD: return a recoverable typed error
and retain delivery of the original message, not silent clamping or discard.

`correctTimestampIfNeeded` now returns `TimestampRangeError(receiveTime)` when
correction is needed but the receive time's truncated Unix seconds cannot fit
UInt32. Ingestion logs the error at ERROR level and continues with the original
sender stamp/text, `timestampCorrected=false`, unchanged content dedup/RX lookup,
and the original receive/sort dates. A later healthy clock resumes normal
correction. This does not mark the connection or sync phase failed.
The production App graph sends sync log entries through `PersistentLogger`, reaching
both the platform logger and the process debug-log buffer. The App integration case
asserts the range error at ERROR level on both diagnostic paths while retaining delivery.

The conversion uses integer seconds/nanoseconds, not a rounded Double. Truncation
toward zero matches the source conversion: a time just before epoch converts to
zero, and the fractional second above UInt32.max still converts to UInt32.max;
whole seconds -1 and 4294967296 fail. These are native decision-boundary tests,
not claims that the Swift trapping inputs executed successfully. Other uses of
the existing date clamp (wire-date helpers, watermark and reaction anchors) are
unchanged and not newly approved by this repair.

New pure boundary cases and wired handler cases cover both ends, direct/channel
delivery, live/backlog sort dates, typed diagnostics, original text, dedup and
notifications. `TimestampRangeRecoveryTest` additionally exercises the actual
poller, production session graph, Room persistence, process message consumer and
subsequent clock recovery. Authored cases require exact-candidate hosted
execution before acceptance; no historical pass transfers.

Review exposed the App's previous no-op default sync logger (support issue #489).
The production Android factory now explicitly routes every sync level through the
existing `PersistentLogger`, retaining explicit sink injection. ERROR diagnostics enter the
session's real `DebugLogBuffer` and Room debug-log repository; each App recovery
test flushes that buffer and requires the persisted range diagnostic before
checking duplicate replay and healthy-clock recovery. This adds no analytics or
external logging service.

The six previously accepted concern repairs remain unchanged. The activity-order
repair below retains the strict wall-time predicate separately from causal
ordering; this change does not approve their equivalence.

## A-01: shape

The Swift actor becomes lock-confined state (`SyncCoordinatorState`). Every
check-and-set happens in one `synchronized` block that never suspends, so the claim
checks (`isSyncInProgress`, the advert/manual flags, waiter registration) are as atomic
as the actor's synchronous segments. `@MainActor` state (`state`, versions,
`lastSyncDate`) is backed by `StateFlow`s. Background work (suppression watchdog,
discovery monitoring, both retry loops) runs in an injected `CoroutineScope`; every
`Date()`, `ContinuousClock` and `Task.sleep` goes through an injected `SyncClock`.

The Swift extensions on `ConnectionManager` (`ConnectionManager+SyncRetry.swift`, plus
`detectAndStorePlatform` and `shouldPauseWiFiHeartbeatProbe`) become
`SyncRetryController`, driven through the `SyncRetryHost` port. `core:services`
cannot depend on `core:runtime`; the host members mirror the runtime
`ConnectionManager` getters of the same names (`connectionState`,
`detectedPlatform`, `lastCleanChannelSync`, `lastAttemptedChannelSync`).

## A-03: cancellation

Kotlin cancellation is prompt at every suspension point. Swift is cooperative, and
several Swift catch-alls absorb `CancellationError`. Kotlin never swallows the
*caller's* cancellation. It runs the same cleanup in `NonCancellable`, then rethrows:

- `runFullSync`: end the activity bracket once, then reset to idle (as Swift).
- `performResync`: drain handlers and resume notifications and auto-fetch, then rethrow.
  Swift returns `false`. Its success-path drain and resume are non-cancellable too.
- `onConnectionEstablished`: drain, resume and release the advert deferral, then rethrow.
- `retryChannels`: a cancelled advert wait rethrows. Swift returns a
  "Retry cancelled" result. Any cancellation after the claim (including one inside an
  activity callback) closes the bracket once and sets idle, then rethrows.
- `performAdvertContactSync`: cancellation rethrows. Swift returns `.failed`. WP-209's
  round already treats a cancelled handler as a cancelled round.
- `SyncRetryController.performInitialSync`: rethrows. Swift starts the resync loop.
- `onDisconnected` runs entirely in `NonCancellable`, because it is the safety net for
  stuck suppression and pills.

A `CancellationException` that a collaborator raises while the caller is still active
(an internal `withTimeout`, a foreign job) is an ordinary failure. Swift only
special-cases its own `CancellationError`, so a contact-stream timeout still gives
`.failed` and starts the resync loop.

In the resync loop, the bracket open, the success close plus promotion, and the
exhaustion branch (`onResyncFailed`, then the disconnect that cancels this same loop)
run in `NonCancellable`. The remaining success hooks (time sync, room re-auth,
`onDeviceSynced`) stay cancellable, with the cancellation and graph fence checked
between them where Swift checks. Both loop bodies catch and log any non-cancellation
throw instead of failing the scope. The injected scope should still carry a
`SupervisorJob`.

## A-04: collaborator failures

Swift declares most collaborator members non-throwing. Their Kotlin ports can throw.
Each such call (notifications, reaction index/queue/persist, heard-repeat
recording/harvest, RX-log cache updates, advert hooks, admin routing, activity and
phase callbacks, auto-fetch control) is wrapped. A throw is logged and the next step
runs, as if the Swift call had returned. Message handlers, the discovery monitor and
both retry loops can't be ended by a collaborator throw, and nothing reaches the
uncaught-exception handler. A `CancellationException` that a collaborator raises
while the caller is still active (an internal timeout) is logged as a failure.
Throwing members keep Swift's own `do/catch` and `try?` placement.

## A-05: claim ownership

Swift's `defer { isSyncInProgress = false }` can clear a newer claim. `onDisconnected`
clears the flag, a reconnect sync claims it, and then the old sync's `defer` clears
the reconnect's claim. The flag now carries a generation that every claim and
every disconnect bumps. A release only clears the claim it still owns. The advert
release still always wakes waiters. Native case:
`WP-214::a claim released after a disconnect cannot clear a newer sync's claim`.

Similarly, a resync or channel-retry job clears its stored slot only if it still
owns it. Swift checks `!Task.isCancelled` for the same purpose. The resync attempt
count is per loop.

`claimManualContactSync` re-checks the advert claim in the same critical section that
sets the manual flag, which closes the gap between Swift's two actor segments.

## A-06: Swift text semantics

- Blocked-sender lookup and the "message from my own node" self-mention check use
  canonical equivalence (NFC keys), matching Swift `String ==`/`Set<String>`.
- `parseChannelMessage` splits on `:` `Character`s (`\X` grapheme clusters). A colon
  that carries a combining mark isn't a separator. Only appended pieces count toward
  `maxSplits` (`"::a:b"` gives `a`/`b`). Trimming uses Foundation's
  `CharacterSet.whitespaces` exactly: tab, space, NBSP, U+1680, U+2000-U+200B, U+202F,
  U+205F and U+3000. That set includes U+200B and excludes U+180E. All of these values
  were captured from `swiftc` and are in `evidence/WP-214/swift-oracle/`.
- No regex shorthand classes are used. `\X` is supported by both the JVM and ICU, and
  merged `core:protocol` already uses it.

## A-07: numeric and Foundation edges

- `UInt32(date.timeIntervalSince1970)` traps when the truncated integer cannot fit
  UInt32 in Swift. The original Kotlin clamp remains for sender stamps and the
  watermark reference. Receive-time correction instead follows the approved
  recoverable-error/retain-delivery decision above.
- The reaction window `anchor + 300` saturates at `UInt32.max` instead of trapping.
- `Dictionary(uniqueKeysWithValues:)` traps on a duplicate channel slot. Kotlin keeps
  the last row.
- `error.localizedDescription` becomes the throwable's message (or its class name).
  `SyncCoordinatorError` messages are the Swift `LocalizedError` strings.

## A-08: identity and lifetime

- Swift `fetchContact(id:)`, `fetchRemoteNodeSession(id:)`, unread updates and similar
  calls are keyed by `EntityKey(radioId, id)` in the Android store. Sync passes the
  connection's radio. Room notifications look up the session on the handler's radio.
- Swift closures capture the coordinator `[weak self]`. Kotlin captures it strongly,
  so teardown must clear the polling handlers and the advert delta handler, cancel
  discovery monitoring, and finish data events (see the wiring section).
- `SyncDataEventBroadcaster` registers at `subscribe()` and unregisters when collection
  ends or `finish()` runs. Swift unregisters on deallocation. **A caller that subscribes
  must collect, and must collect each returned flow once.** A flow that is never
  collected stays registered and buffers until `finishDataEvents()`.
- `setState` writes the state flow and invokes `onPhaseChanged` without Swift's
  `@MainActor` hop. Concurrent writers (only possible across overlapping sync paths)
  may see callbacks out of order. The UI callback should read `stateFlow` rather than
  rely on callback order.
- `claimManualContactSync` keeps one deadline across re-waits, so repeated advert
  re-claims cannot stretch the 200 s bound.
