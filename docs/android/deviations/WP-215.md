# WP-215 notification policy and action transactions

Reference: `db14559b39d32322b06477c6ae676112f583db50`. The bounded receipt prerequisite's
current base, head and candidate-specific verification are recorded in
`docs/android/evidence/WP-215/receipt-prerequisite.md`.
**External contribution:** prepared outside the dispatch controller, with no lease,
session or receipt. These are proposed adaptations for coordinator review. The code
is pure JVM: `core/services/.../services/notifications/` plus one contract file in
`core/contracts/.../contracts/notifications/`.

## A-01: shape and lifetime

Swift builds one `NotificationService` and one `NotificationActionHandler` per
`ServiceContainer`, which is per connection. Kotlin keeps that: both are per radio
session. `NotificationService.radioId` qualifies the bare Swift contact and session
UUIDs as `EntityKey`s. `@MainActor` state becomes `@Volatile` fields, an
`AtomicReference<ActiveConversation>` (so `setActiveConversation` stays one atomic
assignment), and a lock for drafts and the pending badge job. No lock is held across
a suspension.

## A-02: delivery split (WP-401)

All `UNUserNotificationCenter` work goes through `NotificationDeliveryPort`. It covers
authorization, category registration, posting, badge, listing delivered notifications
and removing them. The WP-401 process adapter implements it. The new contract types
live in `contracts/notifications/NotificationDelivery.kt`, because
`platform:notifications` can't depend on `core:services`:

- `NotificationCategory` and `NotificationAction`: the Swift enums with the same raw values.
- `NotificationPayload`: a sealed, typed replacement for the `userInfo` dictionary,
  with one case per Swift `type`. Contact and session ids are `EntityKey`s, and
  channels carry a `RadioId`.
- `NotificationRequest`, `DeliveredNotification`, `NotificationResponse`,
  `NotificationAuthorizationStatus`, and `NotificationCategoryDefinition`/`NotificationActionDefinition`.

These existing types are reused unchanged: `NotificationStringProvider`, `NotificationId`,
`NotificationPostResult`, `NotificationPreferencesPort` and `AppStateProvider`.
`PlatformPorts.kt` is not edited. Posting does not use `NotificationPort` or
`NotificationCommand`, for two reasons. `NotificationCommand` requires a `radioId`
and a `Destination` for every notification, and low battery has neither. It also
has no category (which decides the reply/mark-read actions), no thread id, no
numeric badge, and no way to tell a reaction tap or a new-contact tap from a chat
tap. The new-contact destination depends on a tap-time setting, as in
`NavigationCoordinator`. `DeliveredNotification.payload` is null for notifications
that WP-215 did not post, such as WP-402's connection status, so removal can never
touch them.

Dropped iOS-only details: `customDismissAction` (Swift's dismiss handler does
nothing), and the provisional/ephemeral authorization states.

## A-03: foreground presentation

Android has no `willPresent`. `shouldPresentWhileForeground(payload)` ports the Swift
delegate's key checks exactly. Contact keys also cover new-contact, failure and
direct-message reaction payloads. A channel needs both the index and the radio to
match. At post time, if `AppStateProvider.isInForeground()` is true and the payload
belongs to the conversation the user is viewing, the post is skipped. The badge
refresh after it still runs, which is the iOS outcome: the notification is
delivered with no presentation options. If the foreground check fails, the
notification is shown.

## A-04: preferences, badge and clock

- The Swift 5 s `NotificationPreferences()` cache becomes a read of
  `NotificationPreferencesPort.preferences.value`. That value is already an in-memory
  snapshot, so changes apply right away rather than up to 5 s later. Each post method
  reads it once and uses that one snapshot for every gate, sound and badge decision.
- `getBadgeCount` becomes the constructor-injected `NotificationUnreadCounting`. There
  is no "not yet wired" window, because WP-303 builds the service already wired. A
  failure yields zeros, as the Swift closure's `catch` does.
- The badge debounce is 100 ms on the injected `NotificationClock`. A later call
  cancels a pending update. The cancelled caller returns without updating, as
  Swift's awaited task does. Once the debounce has passed, the update runs
  `NonCancellable`, mirroring Swift's non-cooperative `performBadgeUpdate`. A failed
  sleep is ignored, matching Swift's `try? Task.sleep`. Computations are serialized by
  a coroutine `Mutex` in start order. An older read that is still running when a newer
  update starts therefore lands first, and the newest read always wins. On the
  MainActor, Swift could interleave two reads across the store suspension and let the
  older one land last.
- `badgeCount` and `batteryPercentage` are `Long`, the type `NotificationStringProvider`
  and `UnreadCounts` already use.
- Identifiers use upper-case UUID strings, matching Swift `uuidString`. The
  time-stamped suffixes (`reaction-…`, `quick-reply-failed-…`) use
  `epochSecond.nanos` from the clock. They only need to be unique.

## A-05: stale radio and cold start

- **Mark-read** writes use the action's own keys, so they always land on that radio's
  rows: `EntityKey(contact.radioId, messageID)`, `(radioId, channelIndex)` and the
  room session key. They never use the session's radio. Swift's store is global by
  UUID, so the result matches.
- **Quick reply** for a contact or channel of a radio other than the session's is
  not transmitted. It takes the not-ready path: a direct reply saves a draft and
  posts a failure notification, and a channel reply posts a failure. Swift would
  send the text through whichever radio is connected and store it against the old
  radio. The failure payload keeps the contact's own radio. WP-208's
  `MessageService` rejects such sends too.
- **Drafts** are keyed by `EntityKey` (radio plus contact id) rather than the Swift bare
  UUID, so a same-UUID contact on another radio never receives the draft. Drafts stay
  in-memory per session, as in Swift. `consumeDraft` is answered by the session that
  saved the draft. WP-303 must route the chat screen's `consumeDraft(contact.key)` to
  the current session's service. A draft saved for a foreign-radio contact, after a
  radio switch, is therefore kept only for that session's lifetime. It is lost on
  teardown, just as every Swift draft is lost when its container goes.
- **Before `configure()`**: readiness is `false`, as Swift's default `{ false }`, so a
  reply saves a draft and posts the failure notification. Reaction notifications
  are suppressed. A response that arrives before the app installs its forwarders is
  dropped, as Swift's optional callback call does.
- **Permission denial** never blocks messaging. Posts return early or log
  `PermissionDenied`/`Unsupported`, and the reply and mark-read transactions don't
  depend on any post result.

## A-06: failure containment and cancellation

Swift cannot throw from `NotificationService`, the app closures or the action
callbacks. Their Kotlin counterparts can. Every delivery call, the foreground check,
unread counting, `isConnectionReady`, `localNodeName` and the response callbacks are
contained: the failure is logged and Swift's non-failing outcome is used. Swift's
`try?` reads map to contained `null`s. After a successful send, each follow-up step
(clear unread, remove delivered, badge, `notifyConversationsChanged`) is contained
separately. A Kotlin collaborator failure therefore can't turn a sent reply into a
"not sent" report. Mark-read keeps Swift's single `do/catch`: a failed write stops the
rest. A throwing `localNodeName` suppresses the reaction notification rather than
risk a self-notification. A `CancellationException` is always rethrown. The badge
job contains its failures, so it can't fail the injected scope.

Swift's tails are not cooperative: once a reply is sent or the mark-read writes land,
the rest runs even if the task is cancelled. Kotlin runs those tails in
`NonCancellable`. For a reply that is clear unread, remove delivered, badge and
`notifyConversationsChanged`. For mark-read it is remove delivered, badge and notify,
after the writes. Swift's catch-all also catches `CancellationError` from the send and
falls through to the draft and failure notification. Kotlin does the same in
`NonCancellable`: it saves the draft and posts the failure notification (channel:
failure only), then rethrows.

## A-07: Swift text semantics

- `reactionPreview` counts and prefixes Swift `Character`s (extended grapheme clusters,
  via `\X`, as `core:protocol` and `core:model` already do).
- The self-reaction check compares names by canonical equivalence (NFC), matching
  Swift `String ==`. It is not case-insensitive.
- Expected values come from `swiftc` 6.3.2: `evidence/WP-215/wp215_text_oracle.swift.txt`
  and its `.out`.

## A-08: collaborator ports (WP-303 wiring)

| Port | Swift dependency | Owner | Future implementer |
| --- | --- | --- | --- |
| `NotificationMessageSending` | `MessageService.sendDirectMessage`/`sendChannelMessage` | WP-208 | `messaging.MessageService` (`MessagingSendPort`; channel receipt discarded) |
| `NotificationRoomReading` | `RoomServerService.markAsRead(sessionID:)` | WP-210 | `remote.RoomServerService.markAsRead(session)` |
| `NotificationConversationsNotifying` | `SyncCoordinator.notifyConversationsChanged()` | WP-214 | `sync.SyncCoordinator` |
| `NotificationUnreadCounting` | `AppState` `getBadgeCount` closure | WP-303 | `{ dataStore.getTotalUnreadCounts(radioId) }` |
| `NotificationClock` | `Date()`/`Task.sleep` | WP-215 | `SystemNotificationClock` |
| `NotificationDeliveryPort` | `UNUserNotificationCenter` | WP-401 | platform notification adapter |

Persistence is merged `PersistenceStoreProtocol`. `NotificationService` exposes WP-209's
`ContactCleanupNotifications` members with identical signatures
(`removeDeliveredNotifications(contactId: UUID)`, `updateBadgeCount()`). It also
exposes WP-214's `SyncNotificationServicing` posting members. WP-214's
`isSuppressingNotifications()`, `setSuppressingNotifications(...)` and `active*()`
suspend getters map one-to-one onto the service properties of the same meaning. A
native case compiles adapters for both ports with named arguments.

WP-303 must:

- build the per-session service with that session's radio, the delivery adapter,
  the preferences store, the app-state provider, unread counts and the session scope;
- call `setStringProvider` and `setup()` on connect;
- `configure(isConnectionReady, localNodeName)` the handler;
- install the `on*` forwarders to the handler or navigation;
- route `NotificationResponse`s from WP-401 to the current session's `didReceive`;
- clear the forwarders on teardown, as `ServiceContainer.tearDown` does.

## A-09: review

A read-only line-by-line review against the Swift found no divergence in policy,
strings, identifiers or routing. Its concurrency and test-gap findings were all fixed,
each with native regressions that fail without the fix (see the evidence mutations):

- MEDIUM: the post-send and post-write tails are now non-cancellable.
- LOW: a cancelled send keeps the draft and the failure notification.
- LOW: badge computations are serialized.
- LOW: preferences are read once per post.
- LOW: drafts are keyed by `EntityKey`.
- Test gaps: the debounce duration, step order, cancellation propagation and failure
  ids are now asserted.

## A-10: tests

All 20 source ids run under their exact names. Swift's `NotificationService()` and
`ServiceContainer.forTesting` become a fake-backed `NotificationHarness`. The Swift room
suppression test runs unauthorized, so it passes on the permission guard alone. The
port authorizes first, so the suppression guard is what it actually checks.

## A-11: isolated action receipt prerequisite

The independently reviewable [receipt prerequisite](../evidence/WP-215/receipt-prerequisite.md)
extracts the existing WP-215 process-memory contract without changing consumers.
It preserves acceptance, uncertainty and proof-backed non-dispatch as distinct
outcomes, including `wireNotDispatched()`. Acceptance is a successful command
return, not recipient delivery; only the protocol dispatch owner can prove that
an in-flight attempt was not dispatched. A failed persistence row or cancellation
alone never supplies that proof. Mark-read commitment is not wire acceptance.

This bounded contract does not complete WP-215, satisfy its service dependencies,
or authorize #514 integration before #535 actually merges.

## A-12: rejected action custody before dispatcher admission

The separate [capacity-recovery draft](../evidence/WP-215/notification-intake-capacity-recovery.md)
addresses original RemoteInput loss when the process dispatcher refuses its
33rd pending action. Only a genuine capacity rejection enters private recovery;
accepted FIFO and accepted/uncertain transport receipts are unchanged. Original
untrimmed text and typed target metadata are retained for explicit copy/discard,
never automatic channel-slot replay.

The Android adaptation uses bounded app-private SQLite custody plus a separately
bounded, explicitly process-only fallback when storage cannot commit. Neither
fallback exhaustion nor an unavailable foreground launch is mislabeled as
acceptance or durable retention. Closing or cancelling recovery does not delete
records; only explicit discard or confirmed clipboard transfer can do so.

This is currently an incomplete local source draft: its eleven English resource
keys were added only after #620 landed and fresh trusted path/operation admission.
No denied resource or policy was edited, and its 53 authored controls have not run. A source-reviewed
stale-dialog acknowledgment race is repaired by matching the displayed custody
version; unseen newer failure flags are not cleared by an older dialog. It is not build,
process-death, native storage, held-source or overall WP-215 acceptance evidence.

Rejected custody no longer performs SQLite work on the receiver main thread.
A separately bounded FIFO worker uses `goAsync()` and exactly-once pending-result
completion, including a nominal eight-second deadline. Timeout is an unconfirmed
outcome, not a cancelled or proven absent commit; timed-out work keeps its budget
until it settles. Process death after broadcast completion can lose uncommitted
input. Authored ordered-broadcast and handoff controls are not native deadline or
process-kill evidence.
An independent status-only foreground snapshot keeps loss/manual-open warnings
visible while custody is blocked. Unavailable records are not empty records;
closing that surface acknowledges neither unseen records nor failure flags.
Signal-free startup does not show that incomplete warning; failed storage reads
remain incomplete rather than acknowledging unknown durable records.
Pending and completed-failed read dismissal are distinct even at one generation,
preserving newly known process-only copy access. Successful disposition uses its
refresh rather than dismissing the latest live generation, so concurrent loss
warnings remain visible.
Host-owned disposition busy/error state also survives temporary item replacement,
so a real failed Delete is not lost when a later read restores its original.
That operation scope remains mounted during competing-dialog deferral. Copy and
Delete recheck live busy state inside the callbacks to reject duplicate admission
before recomposition or through a retained enabled callback.
