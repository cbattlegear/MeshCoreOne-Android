## Why this is a bounded slice, not full WP-218

The manifest's WP-218 title spans `LinkPreviewService(+Scrape)`,
`MalwareDomainFilter`/urlhaus list, inline image cache/prefetch,
`ElevationService`, `Geocoder`, `LocationService` and `RegionResolver` --
fifteen original Swift sources and roughly 154 original test
assertions/parameter families across URL safety, malware filtering, image
header/byte-cost accounting, link-preview scraping/caching, and
location/geocoder/elevation/region behavior. `verification.configured` is
`false` for this WP and declares no approved commands; this is also the
first commit to ever populate `android/core/services/src/`.

Implementing all fifteen files from one unreviewed pass would not let a
reviewer coherently check adaptation decisions (HTTP client substitution,
image decoding substitution, location/geocoder native boundaries) against
the pinned source in one sitting. Per the android-port-wp skill, a macro WP
too large for coherent review is split by amendment rather than implemented
from partial context. This increment implements and fully verifies only the
two foundational, pure-JVM-portable safety primitives that every later
slice (scraping, image fetch, prefetch) must depend on:

- `UrlSafetyChecker` (ported from `MC1/Utilities/URLSafetyChecker.swift`)
- `MalwareDomainFilter` + `MalwareDomainParser` (ported from
  `MC1/Utilities/MalwareDomainFilter.swift`)

A second commit on this same branch/PR adds two further self-contained,
pure-string/byte primitives with no network/file/location I/O of their own
(see "Second increment" below): `ImageUrlClassifier` and
`ImageHeaderDecoder`.

The remaining original files (`LinkPreviewService`/`LinkPreviewScrapeService`,
`DecodedPreviewCache`, `ImageURLDetector` (the UIKit/ImageIO-dependent
decode/downsample half; its URL-classification half is now ported as
`ImageUrlClassifier`), `InlineImageCache`, `InlineImagePrefetcher`,
`InlineImageDimensionsStore`, `ImageByteCost`, `ElevationService`,
`Geocoder`, `LocationService`, `RegionResolver`, `RedirectSafetyDelegate`,
`CLLocationCoordinate2D+ValidFix`, `LinkPreviewPreferences`, and the
`urlhaus-filter-hosts-online.txt` resource) are explicitly **not**
implemented here and remain open WP-218 scope for a follow-on amendment.
Each of these requires either a persistence/network/location adapter port
(not yet proposed) or a module-graph change (a real Android-side adapter

## What this increment implements

`android/core/services` gains a `content` package, consuming only
`core:protocol`/`core:model`/`core:contracts` plus `kotlinx-coroutines-core`
(already an admitted coordinate family at 1.10.2 for this build; no new
major dependency). It is pure JVM: no `java.net.http`, `java.awt` or
`javax.imageio`, consistent with `core:services` having no Android
dependency.

**`UrlSafetyChecker`** ports the pinned source's SSRF-prevention checks
exactly:
- Scheme allow-list (`http`/`https` only); all other schemes (`file`,
  `javascript`, `data`, schemeless/relative) rejected.
- A literal CDN host allow-list (`media.giphy.com`, `i.giphy.com`) that
  bypasses IP checks, matching the pinned source.
- Hand-written (no-DNS) IPv4/IPv6 literal parsers reject loopback
  (`127.0.0.0/8`, `::1`), unspecified (`0.0.0.0`, `::`), link-local
  (`169.254.0.0/16`, `fe80::/10`), private (`10/8`, `172.16/12`,
  `192.168/16`, `fc00::/7`), multicast/reserved (`224/4`, `240/4`,
  `ff00::/8`) and IPv4-mapped IPv6 (`::ffff:a.b.c.d`) addresses by
  recursing into the embedded IPv4 check. These are custom parsers rather
  than `InetAddress.getByName`, because that JDK API performs real
  hostname resolution for non-literal input (e.g. `getByName("localhost")`
  resolves to `127.0.0.1` on this host), which would have produced a false
  positive against the pinned `isPrivateOrReserved("localhost") == false`
  case.
- DNS-based resolution for non-literal, non-allow-listed hosts, with every
  resolved address checked against the same private/reserved ranges and a
  5-second timeout that fails closed (timeout, DNS failure, and
  cancellation all resolve to "unsafe"). The resolver is an injectable
  `suspend (String) -> List<InetAddress>` lambda (default:
  `InetAddress.getAllByName` on `Dispatchers.IO`); tests inject a
  deterministic fake so no real DNS/network traffic occurs during
  verification, per the "loopback/control DNS/TLS only TEST; never fetch
  real... URLs" constraint.

**`MalwareDomainFilter`/`MalwareDomainParser`** port the pinned actor's
coalesced-load, exact-match lookup behavior:
- `MalwareDomainParser.parse` mirrors the source's URLhaus hosts-file
  parser: skip `#` comment lines, split each remaining line on the first
  space, keep the second token as the domain.
- `MalwareDomainFilter` coalesces concurrent `isBlocked` calls behind a
  single invocation of an injected `loadDomains: suspend () -> Set<String>`
  adapter (via `Mutex` + `CompletableDeferred`), matching the source's
  `ensureLoaded`/single-load-task behavior. `isBlocked` is an exact
  set-membership check; empty hosts are never blocked.
- The actual disk-cache/bundled-snapshot/network-refresh adapter that
  resolves `loadDomains` (and the `urlhaus-filter-hosts-online.txt`
  resource it is bundled from) is **not** implemented here -- it is a
  narrow native-adapter responsibility explicitly deferred to the
  follow-on amendment, consistent with "do not add... online urlhaus
  updater" for this increment and with core:services' pure-JVM boundary
  (bundled-asset/disk I/O is an Android-module concern).

No persistence layer, preference store, or second copy of
`LinkPreviewPersisting`/DataStore preferences is introduced; both types are
pure in-memory logic with injected suspend-function adapters for every
I/O-performing or impure edge (DNS resolution, domain-list loading),
leaving actual HTTP/disk/bundle wiring to the native-adapter layer the
manifest's own boundaries already assign outside `core:services`.

## Second increment: image URL/header primitives

Added in a follow-up commit on this same branch/PR, after coordinator
feedback that the first increment left `android/core/services/build.gradle.kts`
and `android/gradle/dependency-locks/core-services.lockfile` edits
undisclosed against the manifest's declared `write_paths` (see "Build/lock
seam disclosure" below -- this increment itself needs **no** build/lock
changes, since it adds no new dependency).

- **`ImageUrlClassifier`** (ported from
  `MC1Services/Sources/MC1Services/Utilities/ImageURLClassifier.swift`):
  pure `java.net.URI` string inspection. Extension allow-list
  (`jpg`/`jpeg`/`png`/`gif`/`webp`/`heic`, case-insensitive) for
  `isDirectImageUrl`; a literal Giphy hosting-page resolver
  (`giphy.com`/`www.giphy.com` `/gifs/<slug>-<id>` and `/embed/<id>` ->
  `https://i.giphy.com/media/<id>/giphy.gif`) for `resolveImageUrl`;
  `isImageUrl`/`directImageUrl` composites. No image decoding, no network
  I/O -- matches the Swift original's own "pure string/URL inspection"
  doc comment. All 17 original `ImageURLClassifier`-scoped cases from
  `MC1Tests/Services/ImageURLDetectorTests.swift` are ported 1:1. The
  remaining cases in that same Swift test file (`isGIFData` magic-byte
  detection, `downsampledImage` thumbnail sizing) belong to the Swift
  `ImageURLDetector` type's UIKit/ImageIO-dependent decode half, which
  stays deferred/open scope (it needs a native bitmap-decode adapter, not
  a pure-JVM port).
- **`ImageHeaderDecoder`** (ported from `MC1/Services/ImageHeaderDecoder.swift`):
  reads pixel width/height straight from the PNG signature + IHDR chunk
  bytes, with no dependency on `javax.imageio` (explicitly a non-Android
  JDK API per this WP's constraints) or any decode library. The original
  Swift test suite (`MC1Tests/Services/ImageHeaderDecoderTests.swift`,
  3 cases) only exercises PNG input error/success paths (valid PNG ->
  dimensions; non-image bytes -> `nil`; empty data -> `nil`); this port
  covers exactly that surface. Other formats (JPEG/GIF/WebP) that
  `ImageIO`/`CGImageSource` would also decode are **not** implemented here
  since the pinned test suite never exercised them -- adding format
  support beyond the pinned original's tested behavior would be scope
  invention, not porting.

Both primitives are pure functions over `ByteArray`/`URI` with zero
dependencies beyond the JDK standard library already in use elsewhere in
this module; no `build.gradle.kts` or lockfile change was needed for this
increment.

- **`BundledMalwareDomainSnapshot`** (new, no literal Swift equivalent --
  the pinned source's bundled-list loading is implicit in the app target's
  own resource bundle, not a separate Swift type): a narrow
  classpath-resource reader (`ClassLoader.getResourceAsStream`, a plain JVM
  API, not Android-specific) that parses the bundled urlhaus file via the
  existing `MalwareDomainParser.parse` and returns the resulting domain
  set, failing loudly (`IllegalStateException`) if the resource is absent
  or parses to zero domains -- never a success-shaped empty blacklist on a
  missing/corrupt resource, per the explicit constraint. This is one
  legitimate `loadDomains` adapter implementation for
  `MalwareDomainFilter` (a bundled-snapshot fallback); it does not
  implement network refresh/disk-cache refresh, which remain open scope
  requiring a true native adapter (platform file-cache paths, connectivity
  signals).

**Policy primitives** (all pure-JVM, in `content/`, consuming only
`core:protocol`/`core:model`/`core:contracts` + already-admitted
`kotlinx-coroutines-core`; no new dependency):

- **`GeoCoordinate`** + `isValidFix` (ported from
  `MC1Services/Extensions/CLLocationCoordinate2D+ValidFix.swift`): a
  coordinate value type plus the pinned source's exact fix-validity
  predicate (latitude in `[-90, 90]`, longitude in `[-180, 180]`, and
  rejecting the exact `(0, 0)` null-island sentinel the source treats as
  "no real fix"). No original Swift test file exists for this extension
  (confirmed via `git ls-tree` on the pinned tree); the 9 Kotlin test cases
  are independently authored against the documented contract, not ported
  1:1 -- disclosed here to avoid overstating source-test parity.
- **`LinkPreviewPreferences`** (ported from
  `MC1/Models/LinkPreviewPreferences.swift` and its
  `LinkPreviewPreferencesTests.swift`, 6 cases ported 1:1): pure policy
  over an injected `LinkPreviewPreferencesSource` port (a narrow interface
  defined locally in `content/`, since `core:contracts` edits are not
  admitted this increment) exposing the same three preference reads the
  Swift type derives from `UserDefaults` -- link-preview enablement,
  cellular-fetch consent, and inline-image consent -- with the same
  derived-permission policy (e.g. inline images require both link-preview
  and image consent). `InMemoryLinkPreviewPreferencesSource` is a
  deterministic in-memory test double, substituting for the Swift test
  suite's per-test `UserDefaults(suiteName:)` isolation; the real DataStore
  producer wiring remains a narrow native-adapter responsibility outside
  `core:services`, not a second preference store.
- **`ImageByteCost`** (generalized from `MC1/Utilities/ImageByteCost.swift`):
  pure pixel-dimension/stride arithmetic (`width * height * bytesPerPixel`
  fallback, and an exact `rowBytes * height` overload for when real stride
  is known), with no `UIImage`/`Bitmap` dependency -- the
  Bitmap-introspection half (reading an actual decoded image's real
  allocation size) is explicitly deferred to the native-adapter layer. No
  original Swift test file exists for this utility either (confirmed via
  `git ls-tree`); the 7 Kotlin cases are independently authored, disclosed
  the same way as `GeoCoordinate` above.
- **`FifoCostBoundedCache<K, V>`** (new generic extraction, not a literal
  1:1 port of any single Swift file): the shared FIFO,
  count-and-cost-bounded eviction policy common to `LinkPreviewCache`'s
  `NSCache` (`countLimit`/`totalCostLimit`), `DecodedPreviewCache`, and
  `InlineImageCache`'s decoded mirror -- insertion-order eviction while
  more than one entry exists and either bound is exceeded, always keeping
  the just-inserted entry even if it alone exceeds the cost budget (per
  the Swift comment "so a large hero is still served once"). It is
  deliberately payload-agnostic (generic `<K, V>` with an injected
  `costOf` function) so the concrete `LinkPreviewCache`/
  `DecodedPreviewCache`/`InlineImageCache` orchestrators can each wrap it
  with their own payload type and concurrency guard in a later increment,
  exactly as the Swift originals each wrap an equivalent single-threaded
  structure in their own lock/actor -- this primitive is explicitly
  **not** thread-safe by itself, matching that same originals' design.
  8 independently-authored test cases (eviction-by-count,
  eviction-by-cost, replace-moves-to-back, always-keep-last-entry, clear).
- **`BundledMalwareDomainSnapshot`** gains its own 3-case test suite,
  asserting against the real bundled resource: domain count > 100, a known
  real entry (`0022a601.pphost.net`) present, and comment lines excluded.

**What remains open** (unchanged open scope, still not implemented):

## Sixth increment: diagnostic console `\r`-redraw clobbering root-caused; file-based raw-failure printer added

CI run `37403142503` (after the fifth increment's `TestListener`/`logger.error`
diagnostic addition) showed `:core:services:test` with `271 tests completed,
8 failed`, but the retrieved log text contained only **two** of those eight
failures' identities, and the surviving fragment of text began mid-word
(`"ith RequestInProgress, not coalesced()"`). This was investigated and
confirmed, via three independent retrieval methods (`gh run view --log`,
`gh api .../jobs/<id>/logs --allow-escape-sequences`, and downloading and
extracting the full `gh api .../runs/<id>/logs` zip -- the official,
non-CLI-truncated per-step log file), to be the *same* stored log content
in all three cases. Root cause: hosted CI invokes Gradle in a mode where the
live test-execution progress UI is rendered using carriage-return (`\r`)
redraws on a single terminal line; when that raw stream is captured and
split into discrete stored log lines, content overwritten by a later `\r`
before a true `\n` is permanently lost. This means a `TestListener`'s
`logger.error(...)` calls -- however correctly implemented -- are routed
through that same live console and are **not reliable** once more than one
or two tests fail in the same task; the fifth increment's diagnostic
addition is accordingly confirmed insufficient on its own (kept in place;
it is harmless and does help when only a single failure occurs).

The correct, already-precedented fix in this repository is `core/runtime`'s
(WP-207) `printRuntimeFailureDiagnostics` task: an `Exec` task that is
`finalizedBy`'d onto the relevant `Test` task(s) (so it always runs after
the Test task fully finishes, success or failure) and spawns a **separate
Python subprocess** that reads the real, already-written
`build/test-results/*/TEST-*.xml` report files from disk and prints each
failing/erroring/skipped testcase's identity and message/stack directly.
Because this subprocess's own stdout starts fresh only after the Test
task's live rich-console rendering has fully stopped, it is not subject to
the `\r`-redraw clobbering above.

there were active child jobs: [SupervisorJobImpl{Active}@...]. Use
`TestScope.backgroundScope` to launch the coroutines that need to be

Root cause of the regression: `async(SupervisorJob(coroutineContext[Job]))`
constructs a standalone `SupervisorJob` object and passes it as the
coroutine's parent-job context element. Unlike the Job an `async`/`launch`
builder creates for itself (which completes automatically once its body
finishes), a manually constructed `SupervisorJob()` instance never
auto-completes just because its one child finished -- it requires an
explicit `.complete()`/`.cancel()` call. Because this one was parented
under the test's own scope job (`coroutineContext[Job]`), after the
deferred's failure was caught and the test body returned, this
`SupervisorJob` was still sitting there `Active` with no remaining real
work, and `runTest`'s mandatory end-of-test cleanup (which requires every
tracked child job to have actually completed) waited the full timeout and
then failed closed exactly as it should -- this is the harness correctly
catching a genuine resource-lifecycle bug, not a flaky/infra failure.

`supervisorScope { ... }` block wrapping only the expected-failure
`async`/`await` exchange. `supervisorScope` is a suspend function whose
own internal job (a) still isolates a child's failure from propagating to
the caller exactly like the ad hoc `SupervisorJob` did, but (b) completes
automatically once its block body returns and all of its own children have
finished -- so it leaves no dangling tracked job for `runTest`'s teardown
to find, closing the regression without reintroducing the original
parent-cancellation race.

## Eighth increment: `:app:lintDebug` MissingPermission error on `LocationManagerLocationProducing.requestLocation` -- real production bug, fixed with an inline permission guard

CI run `37411366890` (commit `1346eddf`, the seventh increment above)
confirmed `verifyScaffoldTests`'s evidence-shape check now passes --
`core/services`'s own suites, the TSV, and `SUITES` all agree -- and the
build progressed past that gate entirely for the first time. It then
failed at a new, later, genuinely different step, `:app:lintDebug`:

```
LocationManagerLocationProducing.kt:125: Error: Call requires permission
which may be rejected by user: code should explicitly check to see if
permission is available (with checkPermission) or explicitly handle a
potential SecurityException [MissingPermission]
            manager.getCurrentLocation(
```

This is a real, previously-undetected production bug in this WP's own
owned file, not an infrastructure or validator issue: `requestLocation()`
called `LocationManager.getCurrentLocation(...)` (which requires
`ACCESS_FINE_LOCATION`/`ACCESS_COARSE_LOCATION` at the call site) with no
permission check guarding that specific call. The adapter's
`authorizationStatus`/`currentStatus()` correctly reports the real grant
state to callers, and `core:services`' own `LocationService.kt` checks
`isAuthorized` before ever invoking this producer's `requestLocation()` --
but that is a *cross-module, cross-call* invariant lint's single-file
static analysis cannot see, and more importantly it does not protect
against the OS revoking the grant in the window between that upstream
check and this adapter's actual platform call (Android permissions are
revocable by the user, via Settings, at any moment -- there is no inherent
guarantee the grant observed a coroutine-suspend-point earlier still holds
now). Without a local guard, a revoked-mid-flight permission would have
caused this call to throw a raw, untyped `SecurityException` instead of
the typed `LocationServiceError.NotAuthorized` state this WP's scope
requires for all no-fix/permission/offline/error outcomes.

Fix: added an inline `context.checkSelfPermission(...) ==
PackageManager.PERMISSION_GRANTED` guard (checking both FINE and COARSE)
immediately before the `getCurrentLocation` call -- not merely a call to
the existing private `currentStatus()` helper, since lint's
`MissingPermission` detector requires the literal guard shape at (or
immediately dominating) the call site to recognize it; a call to another
method it cannot statically see through does not satisfy the check. If
neither permission is granted, the adapter now updates
`mutableStatus`/throws `LocationServiceError.NotAuthorized(DENIED)` before
ever reaching the platform call. A `try`/`catch (SecurityException)` was
also added around `getCurrentLocation` itself as defense-in-depth against
the narrow revoke-after-check race, converting any such late
`SecurityException` into the same typed `NotAuthorized` state rather than
letting it propagate raw.

Updated `LocationManagerLocationProducingTest.kt` (one of this WP's
fixed-allowance native platform test paths) to match the new, correct
precondition: the two pre-existing tests that exercise a successful fix
and a disabled-provider failure now explicitly
`grantPermissions(ACCESS_FINE_LOCATION)` first (reflecting the real
precondition `core:services`' `LocationService` already enforces before
calling this producer), and one new test,
`requestLocation fails with NotAuthorized when no location permission is
granted`, was added asserting the new guard's typed-error behavior and
that it updates `authorizationStatus` to `DENIED` -- a genuine new
positive assertion, not a relaxation of any existing one.

Verified locally: `tools/android-port/portmap.py` clean (exit 0);
`tools/android-port/controller/test_runner.py` 226/226 passed (this is a
Kotlin/Android-only change with no Python-tracked surface, so the
controller suite itself is unaffected either way). No local Gradle/JVM
execution is available to directly confirm `:app:lintDebug`/

on this PR.
