## Issue 398 production-consumer repair

The current repair binds `NotificationNavigationBinding` through the existing
AppState platform hook in `AppContainer`, not a second notification dispatcher.
The production receiver's process queue retries only after the actual current
session/generation has installed its callbacks and again at the runtime's
actual `onDeviceSynced` READY edge. A held contact sync longer than the process
queue's 15-second retry window is covered without adding another dispatcher
or lifecycle monitor. Rewiring the same session keeps
the callback identity; disconnect/shutdown detaches it. Wrong-radio and stale
callbacks cannot commit navigation. Inline reply/read handlers remain owned by
the radio container.

Every newly installed session advances the navigation generation, including
same-radio replacement without a loss callback. Same-radio selection/stacks
are retained; eligible pending confirmations are rebound with a fresh delivery
token so old jobs cannot acknowledge them. An eligible contact URI consumed
during the first handshake survives initial radio assignment, while a request
targeting a different radio (or the newly identified local node) is not rebound.
The mounted regressions cover consumed cold deliveries and captured/in-flight
callbacks across the runtime's actual same-radio session rebuild.
The initial assignment also admits still-pending pre-assignment lookups only
into that exact first generation and a compatible target radio; later clears,
rebuilds and switches invalidate that allowance. A queued chat coroutine that
starts after the handshake still reaches confirmation without automatic import.

The adaptive shell mounts one contact-link confirmation outside its list/detail
entries. Both URI producers preserve claimed name, public key, contact type,
target radio and generation captured before asynchronous lookup (before launch
for in-chat links). Their guarded completion rejects stale saved-contact
navigation as well as stale confirmation staging. Support issue #497 records
this directly necessary WP-405/WP-307 producer repair. Every staged delivery
gets a unique opaque token, including identical URIs and clear/restage changes
that composition does not observe individually. Composition and acknowledgement
use that token; replaced mounted imports are cancelled and cannot navigate on
a late ACK. Local identity lookup precedes Add/View; saved
identity wins while offline. Import requires an explicit button action through
the existing Nodes/contact service, a real stored row, and a current request
before atomic acknowledgement/contact-detail navigation. Dismiss/Back cancels
the owned UI job and cannot acknowledge a replacement link. Cancellation cannot
undo a radio/database write that already committed; no rollback is claimed.
Lookup/import failures are shown and retryable, not interpreted as absent data
or successful import.
Every retry marks loading and shares an operation mutex with confirmation;
overlapping loads cannot reorder persistence results. A saved-contact link
atomically retires any previous pending confirmation/import when navigating.
Both behaviors have mounted held-operation regressions.

Actual mounted execution also exposed the outgoing-entry owner-map crash
documented in support issue #500. Entry ownership now travels immutably with
each entry and is reconstructed from the existing serialized tab field; the
saved-state format is unchanged. Transition/predictive Back never consults

reconciliation monitor remains activation-scoped and starts once in its owned
UI scope; graph retirement is independent of process activation (support #501).
Actual graph withdrawal retires only its matching notification binding in that
same process-owned scope, without clearing retained selection or drafts.
A DISCONNECTED edge may arrive before graph withdrawal and cannot be the sole
retirement signal. Bound callbacks check live graph/token identity before
lookup and at commit, including the held replacement-handshake gap before a
new navigation generation is installed. Rebuild retirement preserves selection
and never clears a successor binding.
The activated disconnect watcher now distinguishes the runtime's in-progress
rebuild from final loss. Its mounted regression starts the actual process and
holds physical teardown after graph withdrawal, then drains a separately
controlled UI scheduler while DISCONNECTED remains current. Retained entry,
selection, composer identity/focus/typing and independent persisted draft are
asserted both in that gap and after the replacement becomes READY.
Both contact producers also capture exact graph validity before lookup and
check it at completion, including saved/absent results in that same held gap.
The initial unbound allowance remains limited to the original first-assignment
context. Stale producers report rejection without mutating a successor's state.
For a first graph already published in the registry while device persistence
still suspends token publication, URI capture admits only that same non-retired
graph and the unchanged unbound navigation generation. Notification dispatch
and RF import retain strict token/readiness guards. A held real device-save
regression exercises found and absent external/chat links, claimed metadata,
mounted cancellation, and subsequent publication of that identical graph.
The outgoing Chats list also acknowledges an already-installed route against
its owning Chats stack, not the newly selected Nodes stack (support #502).
Delayed pending handoffs cannot reselect Chats after a later discovery/contact
notification, while new notification routes still use the direct coordinator.
RF import captures the real Nodes session before suspension and checks it after
the ACK, stored-row lookup and at acknowledgement. A post-commit held lookup
across replacement cannot navigate or consume the pending confirmation; the
committed write is not represented as rolled back. Same-radio selection and
the incumbent retained-composer/draft tests remain required.
Initial radio assignment retains compatible offline contact/chat destinations
and prunes foreign-radio destinations instead of clearing an already-consumed
saved-contact link; a mounted persisted-radio/held-handshake regression covers
both matching and different radios.
The persisted fixture uses the canonical row returned by Room after upsert,
including its preserved UUID across the two connection cases. Mounted chat
assertions verify full destination DTOs and acknowledgement of consumed pending
deliveries rather than expecting already-consumed transient fields to remain.
