# WP-305 onboarding: deviations and type-placement decisions

Source specification: `db14559b39d32322b06477c6ae676112f583db50`. Scope: `android/feature/onboarding/`
only. This is the onboarding feature module, not app-graph wiring (WP-303) and not device-verified.

## Conflict-retained Repeat preparation

The bounded consumer follow-up retains strict creation-receipt revision/authority
checks. A committed, definitely-unsent creation whose cleanup conflicts is fenced
from later enable/restore instead of silently adopting its abandoned RF baseline.
Process-store custody is registered at actual commit and shared across editors and
delegating wrappers. Actual SET acknowledgement or possible transmission preserves
legitimate restore use; pending/UNKNOWN/unsent custody requires an actual committed
snapshot clear. Unrelated edits, changed snapshot fields and equal-value ABA do not
silently release the fence. The feature surfaces the typed failure through its
existing error path; explicit current-token clear resolves it. This is not a new
durable quarantine format or cross-process recovery claim. The actual Room
revision/ABA, manual-RF and fresh enable/off discriminator and exact candidate
results are recorded in the bounded evidence document.

Restore admission also serializes identity/delete/insert writers, with sorted,
deduplicated UUID locking for identity merges and a process identity version for
delete/reinsert ABA. Its permit ends at actual transport-send settlement, not the
firmware response or persistence ACK. Owned protocol completion retains custody
if caller cancellation returns while a send child can still write.

The pinned connection initializer cleared inactive Repeat snapshots only when
frequency was present. Android now clears all four fields on an actual Repeat-off
connection, including frequency-null partial orphans after reopening Room. Reopening
alone leaves rows untouched; active-Repeat partial snapshots retain per-field
fallback behavior. This correction does not change the source pin or introduce a
durable orphan marker.

## Current-main onboarding authority prerequisite

The separately assigned foundation repair uses trusted related-consumer/test capabilities for
the runtime, contracts, persistence and app adapters; it does not extend the feature/UI work above.
Its [bounded evidence](../evidence/WP-305/current-main-authority-foundation.md) records exact producer
sources, the refused historical advisory claim, fresh path admissions and source-only results.

Android device edits now acknowledge an actual optimistic Room commit before live publication,
with generation retirement serialized by runtime write authority. Targeted edits rebase on the
latest stored row rather than saving a suspended caller's full DTO. A retired pre-commit region
edit does not change Room; an already committed edit still finishes bounded live publication and
its notification, including late caller cancellation. Notifications run after persistence/runtime/
editor locks release, retaining their originating token and edit sequence for RX rejection.
The existing RX cases pause at the real CAS or post-commit notification boundary accordingly.

Onboarding completion has one explicit pending-to-sealed/pending-to-rejected CAS. The runtime
validates the active, connected, current generation while sealing; this is not a claim that arbitrary
ancestor-job cancellation is atomic. No radio operation occurs in the seal.

The staged Flags prerequisite now wires durable completion into the actual feature completion
calls. Android completion/reset suspend for acknowledgement; no-device and preset-finish failures
use their existing visible error surfaces, and a preset success tick occurs only after completion
acknowledgement. Flow disposal rejects a pending exact attempt; process shutdown drains the writer
before process cancellation. A sealed finalizer can still commit after caller cancellation.
The next bounded slice wires the actual captured preset target through the awaited app updates
and runtime seal, with its minimal acknowledged preset receipt. It does not import the historical
retained-flow/navigation publication subsystem or claim full onboarding UI acceptance.

OCV live publication uses a runtime-owned monotonic revision captured atomically with the device,
including equal-valued accepted publications. A targeted editor preserves newer live OCV fields
when the revision changed, so DTO equality is not treated as publication identity. The paired
normal/masked-revision control exercises the actual editor merge with a fake access boundary;
it is not claimed as a second Room commit. The separate real-Room A/B/A control is a preservation/
serialization witness, not a discriminating stamp regression: actual commit-callback publication
already closes its old delayed-publication window. Awaited token-bound pre-Repeat editor primitives
and their Room controls are supplied for the Settings owner, not evidence that its consumer is wired.

## Native adaptations

- SwiftUI `NavigationStack` path becomes `OnboardingState.onboardingPath` (StateFlow, immutable list
  copies); the welcome root is the empty path. System back pops the path through a dependency seam.
- Sheets (`.sheet`) become Material3 `ModalBottomSheet`; alerts become `AlertDialog`; Liquid Glass
  containers/buttons become Material3 `Card`/`Button`. Hit targets are 48dp (iOS 44pt).
- `UserDefaults` becomes `OnboardingFlagStore` (same `hasCompletedOnboarding` key).
- Permissions: notifications and location cards are marked **optional** (iOS shows them unmarked);
  "Continue" is never gated. Bluetooth is requested just in time on the first "Add device" tap,
  not on the permissions screen; local-network (API 37) when the WiFi sheet opens. A denied
  permission turns the card/notice into an "Open Settings" action.
- `AccessorySetupKit` pairing is the app's CompanionDeviceManager flow behind `OnboardingPairingPort`.
  `DeviceScannerSheet` (macOS-only in the original) becomes the in-app scan fallback sheet, shown only
  when `OnboardingScanFallbackPort.isRequested`.
- iOS `triggerLocalNetworkPrivacyAlert()` (UDP socket trick) is not ported; Android uses the
  `ACCESS_LOCAL_NETWORK` runtime permission where it exists.
- Simulator-only primary CTA (`targetEnvironment(simulator)`) has no Android analogue; demo mode is
  `OnboardingDemoPort` (3 taps on the pair title unlock it, preserved).
- `MeshAnimationView`/`PulsingAntenna` use Compose Canvas / infinite transition; "Reduce Motion" is
  approximated by animator duration scale 0. Geometry/timing constants are carried exactly.
- Preset frequency uses `Locale.ROOT` `%.3f` (matches `.number.precision(.fractionLength(3)).locale(.posix)`).
- The region/country search is a case-insensitive substring match, not `localizedStandardContains`.
- `DeviceMenuTipCoordinator` is the feature-owned slice of `AppState.donateDeviceMenuTipIfOnValidTab`
  (valid tabs Chats/Nodes/Map). The TipKit donation itself is a callback the app binds.
- Retry alert after a retryable preset failure: the original error is shown below the three-attempt
  limit; at the limit, the dialog shows the localized connection guidance. Acknowledgement then
  shows the generic fallback message (`RetryAlertState.maxRetries == 3` carried over).

## App-layer wiring still required (WP-303)

`FeatureRegistry.kt`/`NativeNavigationShell.kt` still call `OnboardingEntry(route, navigate)` (third
parameter defaults to null, which keeps the honest "not yet ported" shell). The app must pass an
`OnboardingFeatureDependencies` backed by: PairingCoordinator/CompanionPairingService (+ scan fallback),
the connectivity permission state, ConnectionManager/WiFi connect, `RegionResolver`/`RegionalAreas`/
`RadioPresets`/`SettingsService`, demo mode, and the DataStore flag. It must implement
`rememberPermissionRequester` with `rememberLauncherForActivityResult(RequestPermission)` and
`InterceptBack` with `BackHandler` (activity-compose 1.8.2 is locked only for runtime, not on this
module's compile classpath, so the seams live in the app). On completion the entry navigates to the
chats root; the app should also treat `hasCompletedOnboarding` as the source for first-run gating.

## Test-dependency amendment needed for Compose UI tests

The feature lock has only JUnit4 + kotlin-test; no Robolectric, `androidx.test:core`,
`compose.ui:ui-test-junit4`/`ui-test-manifest`, or `kotlinx-coroutines-test`. A future lock amendment

screens compile and lint clean.

# Actual Repeat consumer durable boundary

The pinned Swift Repeat toggle synchronously saves/clears its model snapshot before
or after the radio operation. Android's prior Settings adapter discarded an editor
Job, allowing radio mutation before persistence. The bounded follow-up awaits the
existing session-token editor save before SET and clear after verified restore,
surfaces failure through the existing Settings error/retry path, and retains the
initiating target through confirmation and retry. Every enable/retry re-enters the
authoritative preserving-or-saving transform, even if a stale observation contains
a snapshot. The token-bound event consumer prevents retired RF/Repeat publications
from editing a successor. Existing UI confirmation, busy gating and restoration
fallback fields are retained; no new visible strings or theme behavior are added.

Source controls include the actual holder/adapter/Room/radio path, held native Room
transaction, injected persistence-boundary failures, same-radio successor retirement,
and real serialized RF baseline validation. Execution remains bound to the exact
future candidate run, not the earlier verified foundation. This does not accept
the separately owned manual-radio delayed-observation or broader Settings changes.

A newly created snapshot also needs a cancellation-abort identity. Android records
the actual committed row and both revisions in the attempt before returning from
Room. A narrow cancellation tail may clear only that exact newly created snapshot
under its original session authority, and only before SET or after actual protocol
accounting proves it definitely unsent. Possible wire outcomes retain restoration
data; preexisting partial/full snapshots are never owned by the new attempt.
Revision/DTO mismatch or retirement explicitly refuses cleanup. This prevents a
cancelled pre-wire enable from silently pinning restoration to RF that predates a
later manual edit without weakening authoritative snapshot preservation.
