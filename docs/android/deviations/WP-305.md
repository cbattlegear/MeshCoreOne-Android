# WP-305 onboarding: deviations and type-placement decisions

Source specification: `db14559b39d32322b06477c6ae676112f583db50`. Scope: `android/feature/onboarding/`
only. This is the onboarding feature module, not app-graph wiring (WP-303) and not device-verified.

## Native adaptations

### Device-writer authority support repair for onboarding #532

This bounded follow-up additionally repairs capability-admitted core/App consumers of the preset
completion seam. The source pin is unchanged. The pinned Swift editor optimistically replaces a live
DTO and asynchronously saves a full copy; Android instead serializes editor operations through their
suspending persistence work, derives intended changes from a matching Room ticket, and publishes only
after persistence succeeds. Live publication merges newly authoritative Room fields with changes
published while persistence was suspended. There is no rollback over a newer edit or connection.

Targeted writes (including OCV and contact-sync watermarks) invalidate the write revision but may be
rebased under the same authority. Full replacements, activation and identity changes invalidate the
authority revision and are not transparently retried. Sixteen unsuccessful targeted CAS attempts
produce an explicit conflict rather than an unbounded retry. Both revisions are process-owned
per-device bookkeeping shared by stores using the same Room database instance and protected by its
shared coroutine transaction mutex; the database schema does not change. Independent database
instances/processes are not a supported writer graph or a cross-process revision guarantee.
Session-bound preset/hash methods retain their Boolean stale-session result and persistence failures.
An authority change remains `DeviceEditPersistenceConflict`; a normal Room failure leaves live state
untouched. No JVM monitor is held across coroutine suspension.

The DeviceService callback now publishes only OCV fields under its captured token, not its stale full
DTO. Connection refresh/identity writes rebase their intended changes rather than saving an older
full DTO. Initial connection creation and simulator seeding use an atomic inactive insert-if-absent;
an old initializer cannot overwrite an existing row or select the active radio. Repeated simulator
seeding consequently preserves existing device settings instead of resetting them on reconnect.
Runtime activation holds the same suspending authority mutex as ownership-retiring state transitions
through the actual Room transaction and its revision publication. Session editor tickets carry this
lease to the storage commit, outside the database mutex. The lock order is runtime authority then
database transaction; teardown/service callbacks are not awaited under either runtime state monitor.
The final transaction guard can roll back staged device/channel work, but is not itself a durable
runtime fence. Cancellation before commit rejects the write and releases a queued commit lease
without waiting for an unrelated Room transaction. The existing repository commit worker invokes a
bounded synchronous `onCommitted` callback after the real commit and revision bookkeeping, while
the runtime lease is still held; only this committed live/cache reconciliation survives late caller
cancellation. Snapshot fetches, lease acquisition and pre-commit Room waits remain cancellable.
The BLE reconnection state/clear delegate operations and pairing mark-disconnected call-through are
suspending so they use the same gate, as do restoration-route generation replacements.
Reconnection state/clear is one guarded transition: original runtime owner/revision and reconnect
claim/timer are rechecked after acquiring commit authority. Timeout claim retirement and state/device
mutation occur together, so a queued old timeout or pairing cleanup cannot erase a successor.
Entry/completion suspension belongs inside teardown/rebuild cleanup boundaries; cancellation cannot
leave an unresolved teardown receipt or stuck rebuilding flag.
The actual Settings region consumer awaits token-bound, field-scoped add/remove operations;
default-name clearing is atomic with Room region/channel removal, while radio verification remains
before the deletion. It no longer fetches and republishes an intervening stale full device.

The production-editor/real-Room race cases are in `DeviceWriterAuthorityRoomTest`; they include both
OCV ticket interleavings, post-commit OCV publication, an older OCV save versus a completed preset,
ordinary editor ordering, actual successor activation, the same-token watermark conflict, and actual
Settings region-consumer default/unrelated/concurrent/successor/storage-failure cases. Execution
status and immutable source binding are recorded in the bounded support evidence; source controls
alone do not establish that these Kotlin tests executed.

Ordinary Settings device/auto-add/client-repeat/default-scope events now carry their original token
through awaited editor methods, rather than capturing the then-current connection token. Repeat
frequency overlays also use a token-checked runtime mutation. The separately owned default-scope
service acknowledgment/removal queue follow-up is still required: these editor APIs alone do not
make the existing verified radio operation acknowledge local persistence or pending selection.

- SwiftUI `NavigationStack` path becomes `OnboardingState.onboardingPath` (StateFlow, immutable list
  copies); the welcome root is the empty path. System back pops the path through a dependency seam.
- Sheets (`.sheet`) become Material3 `ModalBottomSheet`; alerts become `AlertDialog`; Liquid Glass
  containers/buttons become Material3 `Card`/`Button`. Hit targets are 48dp (iOS 44pt).
- `UserDefaults` becomes `OnboardingFlagStore` (same `hasCompletedOnboarding` key).
- Permissions: notifications and location cards are marked **optional** (iOS shows them unmarked);
  "Continue" is never gated. Bluetooth is requested just in time on the first "Add device" tap,
  not on the permissions screen; local-network (API 37) when the WiFi sheet opens. A denied
  permission turns the card/notice into an "Open Settings" action.
- `AccessorySetupKit` pairing is the app's CompanionDeviceManager flow behind `OnboardingPairingPort`.
  `DeviceScannerSheet` (macOS-only in the original) becomes the in-app scan fallback sheet, shown only
  when `OnboardingScanFallbackPort.isRequested`.
- iOS `triggerLocalNetworkPrivacyAlert()` (UDP socket trick) is not ported; Android uses the
  `ACCESS_LOCAL_NETWORK` runtime permission where it exists.
- Simulator-only primary CTA (`targetEnvironment(simulator)`) has no Android analogue; demo mode is
  `OnboardingDemoPort` (3 taps on the pair title unlock it, preserved).
- `MeshAnimationView`/`PulsingAntenna` use Compose Canvas / infinite transition; "Reduce Motion" is
  approximated by animator duration scale 0. Geometry/timing constants are carried exactly.
- Preset frequency uses `Locale.ROOT` `%.3f` (matches `.number.precision(.fractionLength(3)).locale(.posix)`).
- The region/country search is a case-insensitive substring match, not `localizedStandardContains`.
- `DeviceMenuTipCoordinator` is the feature-owned slice of `AppState.donateDeviceMenuTipIfOnValidTab`
  (valid tabs Chats/Nodes/Map). The TipKit donation itself is a callback the app binds.
- Retry alert after a retryable preset failure: the original error is shown below the three-attempt
  limit; at the limit, the dialog shows the localized connection guidance. Acknowledgement then
  shows the generic fallback message (`RetryAlertState.maxRetries == 3` carried over).

## App-layer wiring still required (WP-303)

`FeatureRegistry.kt`/`NativeNavigationShell.kt` still call `OnboardingEntry(route, navigate)` (third
parameter defaults to null, which keeps the honest "not yet ported" shell). The app must pass an
`OnboardingFeatureDependencies` backed by: PairingCoordinator/CompanionPairingService (+ scan fallback),
the connectivity permission state, ConnectionManager/WiFi connect, `RegionResolver`/`RegionalAreas`/
`RadioPresets`/`SettingsService`, demo mode, and the DataStore flag. It must implement
`rememberPermissionRequester` with `rememberLauncherForActivityResult(RequestPermission)` and
`InterceptBack` with `BackHandler` (activity-compose 1.8.2 is locked only for runtime, not on this
module's compile classpath, so the seams live in the app). On completion the entry navigates to the
chats root; the app should also treat `hasCompletedOnboarding` as the source for first-run gating.

## Test-dependency amendment needed for Compose UI tests

The feature lock has only JUnit4 + kotlin-test; no Robolectric, `androidx.test:core`,
`compose.ui:ui-test-junit4`/`ui-test-manifest`, or `kotlinx-coroutines-test`. A future lock amendment
needs those (the `mesh.android.robolectric` convention plugin plus `libs.androidx.compose.ui.test.junit4`,
as core:ui uses) to add composable assertions (TalkBack labels, 48dp targets, wide-width layout,
semantics of each sheet). Until then only coordinator/state/animation-model logic is tested and the
screens compile and lint clean.

## Issue #405 software follow-up: completion persistence and donation retry

The onboarding feature now awaits completion-flag persistence before publishing the completed state.
The app's write-behind adapter acknowledges awaited writes only after the process preference store
confirms them; completion writes atomically persist the first-run flag and pending device-menu tip
event. A failed preset-completion write retains the already-applied preset and offers a persistence
retry without applying the radio preset again. The no-device exit likewise stays open and exposes a
retry instead of advancing the first-run gate on a failed write.

`ShowOnceTips` retains the event until an eligible host makes its atomic show-once claim. Device-menu
eligibility now explicitly includes only Chats, Nodes and Map, and tests cover durable reopen,
invalid-tab deferral, valid-tab claims, cancellation/write failure and retry. This does **not** claim
that the native tip is mounted or visually equivalent: the app navigation/tab-change consumer belongs
to the active WP-302 producer, and the approved native tip presentation is still a product decision.
The source's 1.5-second delay before donation is also not represented by this event-persistence
follow-up; do not treat event persistence as display acceptance.

The exact app/core UI tests are not run from this worktree because the shared local Gradle execution
reservation has no cleanup proof. The result remains unverified until the exact candidate runs the
declared hosted tests. No runtime permission, radio, device, Compose rendering, human UI-equivalence,
or full WP-305 acceptance is claimed.

While preset application or its completion write is active, onboarding keeps system Back intercepted
and refuses to pop the flow path. This prevents a process-owned write from completing or failing after
the preset screen has unmounted. Deterministic coordinator tests hold both the radio apply and
completion write, attempt Back at each suspension, and verify the current step is retained on success
and persistence failure. The test does not claim a mounted-device or physical predictive-Back run.
