# WP-311: contacts and discovered nodes

## Contact-detail favorite consistency repair (local source-only candidate)

The frozen Swift detail view keeps a separate favorite value and optional-chains its
service call. This bounded Android correction reflects fresh service/store reads in the
favorite action, rather than retaining the navigation snapshot. Favorite writes now keep
the last confirmed value while pending; the existing action is disabled until completion.
This intentionally avoids presenting an optimistic radio change as confirmed success.
Missing service or a different connected radio reports the existing localized
services-unavailable error. Service failures retain the standard user-facing error.

A screen-local revision protects favorite state across suspended reads, superseded writes
and cancellation. Completion invalidates reads begun during the write as well as reads
begun before it; non-favorite refreshed fields still apply. The selected radio/UUID/public
key remains the read/write target. No rollback is sent or asserted on failure/cancellation:
a radio command may have taken effect before a later failure. A subsequent persisted read
can update the displayed favorite without clearing the failure or proving the radio's state.

## Contact-avatar consumer repair (#520)

### Favorite consistency after avatar save (source-only follow-up)

An additional source-only successor from `b0b6a0a7f17f625d71f894f7c67ad20e339b10a9`
orders overlapping initial, explicit and avatar post-save refresh requests within the
existing screen lifetime. Each read captures its request ticket and favorite revision
before suspension. Only a successfully returned, identity-matching DTO advances the
applied-request watermark. Once a later-requested refresh has applied, older completions
cannot replace any of its fields, including avatar bytes. Merely starting a newer read
does not invalidate an older one: absent, failed, foreign and cancelled reads do not
advance the watermark. The favorite-write revision guard remains independent.

This is deliberate presentation-request precedence, not an assertion that a later-started
read has a higher database version. An older request may itself have observed a newer
external commit; without storage revisions this holder cannot establish durable recency
between arbitrary snapshots. The repair prevents the concrete older-completion overwrite
schedule, permits an older completion while the newer request is still pending, and
allows a subsequent successful request to reconcile state. It does not serialize writes,
change the storage contract, or claim atomic avatar/favorite persistence.

Three additional source-authored controls hold an old initial snapshot while a newer
avatar refresh applies (both favorite directions with exact saved bytes), verify that
unsuccessful/foreign/cancelled newer reads do not discard a valid older result, and check
the opposite completion ordering. Existing failure/cancellation/identity and avatar
observer assertions remain in place. These controls remain unexecuted under the holds.

From parent `8d04a3834f235e6f1742648fada074c364894262`, the existing avatar post-save
contact lookup captures the favorite revision immediately before its asynchronous read and
routes the returned DTO through the same identity/favorite guard as other detail refreshes.
Existing pre/post-save identity assertions and observer stages remain unchanged. Two new
source-authored controls cover both favorite directions for an external persisted change
and for a suspended post-save snapshot spanning a confirmed favorite write. They assert
the exact saved bytes, target identity, final DTO/favorite agreement and observer completion.
The controlled fake-store interleavings are not atomic-storage or radio evidence. No
Kotlin/Gradle/device execution or publication is authorized by this source-only follow-up;
the existing holds and unverified runtime status remain.

The production detail destination now connects native image-only photo/document pickers
to bounded, EXIF-aware decoding, the existing WP-304 crop, real 512x512 JPEG quality-80
encoding and contact save/removal. A streaming 20 MiB compressed-input limit is an Android
memory/privacy adaptation beyond the Swift unbounded `Data(contentsOf:)` read. URI grants
are transient; original media and provider paths are not persisted.

Picker/crop state belongs to the contact's radio/UUID/public-key lifetime. Encoding is
included in saving state; cancellation resets progress and never becomes a success.
Android Activity configuration recreation retains the pending request, decoded crop,
zoom/pan and in-flight action in a ViewModel-owned lifetime. Activity Result registrations
use stable entry/contact identity rather than a holder instance. Each mounted navigation
entry has a separate saveable random token and retained child lifetime, even for the same
contact, so overlapping transitions cannot close or share another entry's work. Only the
token (not contact/media data) enters saved state. Media and URIs are not written
to saved instance state; this is configuration retention, not private process restoration.
Leaving the detail or replacing its identity cancels and clears the lifetime.
Missing service/store and persistence failures are explicit rather than optional-chain
no-ops. Editing is chat-only, preserving the source behavior. The crop component's merged
host-width policy is unchanged. See [bounded repair evidence](../evidence/WP-311/contact-avatar-flow.md)
for actual candidate verification and limitations.

## Adaptations

- **A-1 State holders.** These replace `@Observable @MainActor` view models. Each holds a
  `MutableStateFlow`, an injected `CoroutineScope` and a `NodesClock`. They are confined to the
  main thread like the source. Properties that the source exposes as settable vars are set in
  tests through an `internal seed`.
- **A-2 Cancellation.** The source catch-alls sometimes swallow `CancellationError`, turning
  it into an error message or a `try?` nil. Kotlin always rethrows it. Cleanup still runs: an
  interrupted sync resets `setSyncingContacts(false)` and `isSyncing` under `NonCancellable`,
  and spinners are reset before the rethrow.
- **A-3 String semantics** (`text/SwiftText.kt`). Expectations come from `swiftc` oracles in
  [evidence/oracle](../evidence/WP-311/oracle):
  - `localizedStandardContains` and the picker's `[.caseInsensitive, .diacriticInsensitive]`
    use a per-grapheme fold: NFD, then nonspacing marks removed, then full case folding. A
    dotless `ı` is kept apart, and Turkish/Azeri fold `I` to `ı`. A match must start and end
    on folded-character boundaries. This reproduces Foundation for `ß`/`ss`, ligatures, Kelvin,
    Greek sigma, Hangul and `İstanbul` in `en_US`, no-locale and `tr_TR`.
  - Two known differences remain. Foundation with a locale matches fullwidth `１２` against
    `12`; Android does not. Foundation `localizedStandardContains` matches a member emoji
    inside a ZWJ family; Android does not.
  - `hasPrefix`, `Set<String>` de-duplication and name equality use NFC plus whole-grapheme
    comparison. `isHexDigit` accepts ASCII and fullwidth hex as single scalars. Fullwidth
    input then fails byte parsing, as it does in Swift.
  - `trimmingCharacters(in: .whitespaces)` trims Zs and tab, but not newlines.
  - `localizedCompare` and `localizedCaseInsensitiveCompare` use `java.text.Collator`
    (tertiary or secondary strength, canonical decomposition). This is ICU/CLDR on Android.
    The JVM test runtime uses the JDK tables, which agree on letters but order punctuation,
    spaces and some scripts differently. The owned cases use letters only.
- **A-4 Distance.** `CLLocation.distance(from:)` becomes great-circle haversine distance.
  Orderings only differ for near-equal distances.
- **A-5 Detail delete with no service graph.** The source's optional chain made this a silent
  "success" that dismissed the screen. Android reports
  `detail_error_servicesunavailable` instead of dismissing. The control is radio-gated in
  both versions.
- **A-6 Discovery countdown** uses the monotonic clock instead of `Date.now`.
- **A-7 Share sheet.** `ContactURIActivityItem` (an empty `String` placeholder, so iOS offers
  Copy) becomes a `text/plain` payload whose text is the URI (`ContactShareTextPayload`).
  The actual dialog supplies the existing localized `contactsQrShareSubject`, matching
  `ContactQRShareSheet.swift`'s `L10n.Contacts.Contacts.Qr.shareSubject`; the contact name
  remains the chooser title and clipboard label, not the shared subject. The previous
  contact-name subject was a consumer mismatch, not an approved platform adaptation.
- **A-8 QR and camera.** QR rendering uses ZXing correction level M with fixed black modules
  on white so every unlocked theme remains scannable. CameraX analysis honors Y-plane row and
  pixel stride and closes every `ImageProxy`; permission denial exposes app settings while
  manual URI paste remains available. The QR output round-trips through ZXing in a JVM test.
- **A-9 Avatars.** The resize bounds (512 px longest side, JPEG 0.8) are ported as
  `AvatarProcessing.targetSize`. The completion UI does not yet expose a platform image picker;
  existing avatar data remains displayed by the detail logic and service seam.
- **A-10 Logging.** The source's `Logger`/`PersistentLogger` trace lines are omitted. The
  feature has no logging seam.
- **A-11 Maps.** Contact location uses the shared `MapLibreMapSurface`/OpenFreeMap provider,
  not a second map stack. The detail action can also route to the existing full map feature.
- **A-12 Production recents.** Recent hop order is stored as an ordered JSON string array in
  process `SharedPreferences`; a `StringSet` is intentionally not used because it would destroy
  LRU ordering.
- **A-13 Accessibility/adaptive UI.** Actions have explicit content descriptions, state changes
  use Android announcement events, and the existing WP-302 list/detail scene chooses tiled or
  single-pane presentation from current window size.
