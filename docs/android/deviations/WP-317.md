## Queued default-scope persistence follow-up

The bounded default-scope successor is based on local composition
`2a90aa714490d158d68c1675f9cd40359e5eb139`, which preserves the isolated
`2dfa078fadd21bb4533bcb129f96d10b455fed4a` path-hash lifecycle repair and imports
writer prerequisites `40e6c1e9`, `bd9e98e9`, storage `90cd` as `0e3fbadd`,
`4a01c6c5`, and `8eefab22`. Those writer/runtime/storage changes remain separately
owned. In particular, `8eefab22` is not accepted: its owner is repairing the
separately reviewed runtime cancellation/successor findings in a new prerequisite.
This follow-up does not edit the editor, runtime, Room, or their original tests.

Normal Settings now calls `setDefaultFloodScopePersisted(name, currentDevice)`.
The original-session device callback is sampled inside a session-owned FIFO
completion chain. A nonempty selection must still be a known region after queue
admission; a selection queued behind removal fails with the existing typed,
localized verification error before sending to the radio. Names otherwise retain
the existing UTF-8 normalization and real radio write/readback. A default-scope
event carries an optional durable-write completion, and AppState acknowledges only
the awaited original-token editor result. Errors reach the actual action; retries
retain the original service, busy state spans persistence, and prior action errors
clear on a new attempt. Legacy radio-only APIs/events retain their behavior.

`removeSettingsKnownRegion` enters the same queue before sampling device/radio
scope. Firmware supporting default scope is queried without publishing an
asynchronous stale read; either an actual matching radio scope or a matching
stored scope requires verified clear plus durable acknowledgment before region
removal. This also handles a failed/cancelled selection that changed only the
radio, and an idempotent retry after a clear whose persistence failed. Older
firmware retains removal without an unsupported scope command. Only then does
the callback enter `persistKnownRegionRemoval(region, capturedToken)`; false is
explicitly rejected, and storage errors propagate. The editor mutex is never
held while awaiting the reentrant event acknowledgment.

No monitor is held across queue suspension. Cancelling a queued operation chains
its completion behind its predecessor, rather than allowing a later operation
to bypass a still-running write. Cancelling an active waiter does not roll back
a radio command or an already-entered AppState write. The serial consumer/editor
and subsequent acknowledged clear must finish before removal acknowledges.
Default-scope acknowledgments use the same subscriber-replacement, retired-buffer
and completion-cleanup rules as path hash.

Added controls comprise six actual-service tests, seven actual Settings/radio/
AppState/Room tests, and two feature-action tests. They cover failure/retry,
original token, no consumer, wrong readback, retired/buffered subscriptions,
cancelled queue entries, actual Room contact-watermark CAS rejection, both queue
orders for selection/removal, held persistence, cancellation after event entry,
failed clear with retry, the actual thirty-byte UTF-8 radio-name boundary, busy
state, and original-service retry. Original tests
and assertions remain intact. These are authored controls, not executed Kotlin
evidence. Local readiness and declared manifest/configuration/port-map source
validators passed; no local Gradle runner was used. Exact lifecycle candidate
`2dfa` run `41942349039` remains independently pending at this source handoff;
its result cannot verify this newer default-scope delta.

## Normal Settings path-hash persistence acknowledgment repair

This bounded repair starts from onboarding candidate
`fc7be50b92c275d495932df6e978e95c553ea684` (parent
`94f2fca58f434a5d1bcdef94e0635c2e07cbf201`). The clean worktree matched that
exact base before editing. Swift remains pinned at
`db14559b39d32322b06477c6ae676112f583db50`; no onboarding receipt/flow source,
issue #495 work, schema, runtime writer, or existing draft PR is changed.

The pinned Swift picker awaited radio verification but its event-driven device
save did not acknowledge durable persistence. Android's normal Settings adapter
now uses `SettingsService.setPathHashModePersisted`: real radio write/readback
still happens first, then a token-bearing `PathHashModeUpdated` carries an
optional per-event persistence completion. AppState completes that acknowledgment
only after the existing awaited `updatePathHashMode(mode, originatingToken)`
returns true; false becomes NotConnected and persistence exceptions reach the
original action as failures as well as being logged. The caller waits outside
the radio-operation mutex. Subscription replacement/closure fails outstanding
waiters rather than hanging or claiming success. Existing radio-only callers and
preset events retain their default-null acknowledgment behavior and consumers.

The picker stays busy through persistence, clears its prior error on a new
attempt, and permits any explicit selection after failure, including restoring
the previous persisted mode when the radio alone accepted the failed change.
It also permits reselecting the failed mode if a device update reports that same
mode. Retry-alert actions retain the original Settings service instead
of resampling a successor connection. Ordinary same-mode no-op behavior remains
for successful/untouched selections.

Related service tests cover held acknowledgment with another radio read,
underlying persistence failure and retry, subscriber replacement, absent consumer,
verification rejection, and session retirement. Feature tests retain original
cases and add busy state, error/reselection and service-bound retry coverage.
Actual App tests drive the production Settings dependencies and picker action
through protocol-speaking radio, AppState and Room: a rejecting SQLite trigger
must produce an action error that can be retried; a held conditional save must
keep the action busy; a real contact-watermark update between ticket read and
conditional save must invalidate the original Room ticket and be non-destructively
rebased before success. That last acceptance depends on the separately owned
writer-authority correction; this acknowledgment layer does not implement a
speculative conflict retry or repair the editor itself.

Parent source review of initial commit `a785591c3b534fa0f0e36cf7593541d43d9ee8c9`
identified a discriminating recovery gap: after radio mode 2 verifies but safe
persistence leaves live/Room at mode 0, an explicit mode-0 selection must not be
treated as a clean no-op. The follow-up permits that action while any failure
remains unresolved, with feature and actual Settings/radio/Room restore-to-previous
tests plus a clean same-mode no-write control. Room interception wrappers delegate
the complete `DeviceEditPersisting` interface to the real store, overriding only

The exact predecessor fc7 hosted run `41935019276`, Linux job `126941702081`,
reported two real failures in the existing preset-token suite: expected path-hash

Parent review additionally identified a subscriber-reentry hazard in the initial
acknowledgment implementation: replacing a subscription completed its pending
Deferreds while still holding the outer replacement lock and before installing
the replacement. An unconfined failed caller could install a third subscriber
that the outer replacement would overwrite without closing. The follow-up
atomically detaches pending acknowledgments and installs the new owner under the
lock, then closes channels/completes failures outside it. Finish/close use the
same detached-completion rule. A deterministic real-service test runs the
request and context unconfined, reenters `events()` in the actual failed caller,
requires the outer replacement to be closed and the latest subscriber to
acknowledge a subsequent radio write. This is authored regression coverage,
not executed evidence until its hosted result is available.

Cancelling a caller waiting after radio verification cancels its acknowledgment,
does not manufacture a radio rollback, and propagates cancellation. The holder
retains unresolved recovery state and permits explicitly restoring the previous
mode on reentry. A real-service test checks cancelled pending acknowledgment,
absence of an invented rollback packet, and subsequent verified/acknowledged
restoration through a new subscription; a feature control retains the old-mode
recovery action after cancellation. No cancellation is claimed to undo a write
that a consumer has already committed.

The subsequent fresh-composition review moves recovery authority into the
connection-owned SettingsService: monotonic radio-attempt and acknowledged
revisions identify unresolved path-hash writes even after the UI holder/scope
has been discarded. The feature port exposes that session-owned uncertainty,
and a newly created picker consults it before treating a same-mode selection as
a no-op. An older acknowledgment cannot clear a newer pending attempt. Legacy
radio-only verified writes conservatively leave uncertainty until an explicit
durable Settings write acknowledges the current revision; they still retain
their original radio-only return/event behavior.

Acknowledged path-hash events buffered on a retired subscription are not emitted
to a later collector. This does not discard legacy non-acknowledged event buffers
or claim to roll back an edit that already entered persistence. App integration
controls cover both queued old events followed by a newer acknowledged choice,
and a non-cancellable already-entered Room commit followed by a newer verified
choice: the latter cannot acknowledge until the serialized old commit exits,
and its final Room/live value must remain the newer choice. A mounted API-31
test disposes the actual AppSettingsContent while a verified mode-2 write is held,
lets real Room reject it, recreates the actual composition/holder and explicitly
restores mode 0 through radio readback and durable acknowledgment. The same test
retains a clean same-mode no-radio-write control before the failed operation.
These controls require actual hosted execution; source authorship is not parity.

  `UInt32(String)` for the PIN (no spaces, ASCII only, optional `+`); `NumberFormatter` bandwidth fallback (half-even on the
  exact decimal); `nearestBandwidth` ties; `uppercased()` then ASCII-hex filter (`"ﬀ"` becomes `FF`, `"ß"` and `"ǰ"` drop);
  `CharacterSet.whitespaces`/`.whitespacesAndNewlines` (U+200B is a member); `localizedStandardCompare` ordering of region
  names via `Collator` TERTIARY plus numeric runs. Known residue, not asserted: a stray leading `,` (`",5"` is 5 in Swift) and a
  doubled sign (`"--5"` is -5) are not accepted; the JDK `Collator` can order space/hyphen differently from ICU.
- **A-02 State holders.** Plain classes with an immutable `StateFlow` state, an injected single-threaded `CoroutineScope`
  (Swift `@MainActor`) and an injected `SettingsClock`; an androidx `ViewModel` can wrap each one. `start()/stop()` replace
  `onAppear`/`onDisappear`/`.task`. User edits are separate entry points from device-sync assignments, so Swift's
  `hasInitialized` / `isProgrammaticRepeatToggle` guards are not needed. Swift `@Binding var radioWriteInFlight` is `RadioWriteGate`.
  `CancellationException` is never swallowed; every flag a cancelled write set is released first.
- **A-03 Danger zone.** `forgetDevice` rethrows cancellation (Swift reported a `CancellationError` as an error message).
  A factory reset cancelled during the reboot grace still removes the device (in `NonCancellable`) and then propagates, as Swift
  swallowed the sleep's cancellation and kept cleaning up. A removal cancelled mid-flash clears the transient "Removed" label.
  Removal/forget dialogs and the reset alert are only reachable through the `showing*` confirmation flags.
- **A-04 Retry alert.** `RetryAlertController` keeps `reset()` not touching `isPresented`, and the Retry/Cancel/OK actions that
  `RetryAlertModifier` wired; three retryable failures end in the OK-only "unable to save" dialog that calls the injected `dismiss`.
- **A-05 Location authorization.** `CLAuthorizationStatus` folds to `NOT_DETERMINED/AUTHORIZED/DENIED/RESTRICTED`
  (`authorizedWhenInUse` and `authorizedAlways` both authorized). The two `useMyLocationAction`/`actionAfterAuthorizationWait` cases and the
  four `macOS:` device-selection cases are tagged `platform-adaptation` (the registry-less path is the Android case where no system
  registry validates a device).
- **A-06 Device selection.** `AccessorySetupKit` ids become the companion-association registry ids behind
  `hasSystemPairingRegistry`; `SystemPairedAccessory` is mirrored. The needs-setup row copy returns `UiText`, so tests compare
  resource ids and the formatted label. The English `deviceselection_accessibility_setuplabel` string still says "paired with
  iPhone"; that is a core:l10n content issue for the l10n WP, not changed here.
- **A-07 Navigation.** `SettingsDetail`/`SettingsSubpage` are kept; the iPad split-view selection binding is a host concern.
  `SettingsDeviceHost` is an in-feature page switcher (Done returns to the list); the app may replace it with its own navigation.
  `SettingsEntry.kt` (WP-002 shell) is outside this WP's write paths and was not touched.
- **A-08 Presentation.** Formatted/plural strings need `Resources`, so holders emit resource ids or data (`RemoveOutcome`,
  `footerIds`) and the Compose layer calls the generated `AppSettingsStrings` accessors. `ByteCountFormatStyle(.memory)` is
  approximated by `Formatter.formatShortFileSize`; the last-cleanup relative date uses `DateUtils.getRelativeTimeSpanString`;
  SF Symbols are replaced by text. Voltage is `"%.2f V"`.
- **A-09 Source test fakes.** The Swift `DangerZoneViewModelForgetTests` drives a real `ConnectionManager` with a mock
  AccessorySetupKit; here `FakeMaintenance` raises `PairingCancelledException`. The test is tagged `adapted-service-fake`.
