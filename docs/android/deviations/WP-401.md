## Android notification model

Swift notification categories map to Android 8+ notification channels. Audible and silent variants are
separate because Android owns sound at the channel level. Message categories use `MessagingStyle` and
long-lived conversation shortcuts; other categories use big text. Lock-screen public versions expose only
the app and generic category text.

The existing onboarding/settings flow remains the sole owner of `POST_NOTIFICATIONS` prompting. The
delivery adapter reports the current authorization state and never launches permission UI. Denial or
platform posting failure is a typed notification result and never blocks mesh messaging.

## Actions and process lifetime

Android notification content taps target the module's non-exported `NotificationOpenActivity` with an
immutable activity `PendingIntent`; the typed payload retains the notification-ID action URI and radio,
contact/session/channel/message identity. That Activity stages the response in the existing process
queue and launches a generic package launcher intent with CLEAR_TOP/SINGLE_TOP and no notification
payload. The private entry has no task affinity and starts in a separate transient task; the launcher
uses NEW_TASK to select the normal application task, keeping the private root's excluded-from-Recents
policy from becoming the main application's task policy. Direct reply and mark-read remain explicit, non-exported
broadcast actions. Only the inline-reply `PendingIntent` is mutable. Action extras contain typed
identifiers but no title, body or reply text.

A process-owned queue retains at most 32 cold-start actions and retries for 15 seconds while application
and radio-session state becomes ready. Session creation explicitly retriggers draining. Responses keep the
payload's original radio identity; WP-215 therefore rejects stale-radio transmission while mark-read
targets the payload's own persisted rows.

## Notification content tap repair (#503)

The notification body no longer targets `NotificationActionReceiver`, so opening a notification does not
depend on a receiver/service starting an Activity. Android launches the private Activity directly from
the app-created immutable PendingIntent; it can then open the launcher from an Activity, rather than a
prohibited receiver/service trampoline. The private entry validates the action and payload before
queueing, logs malformed input or missing launcher registration, and always finishes without a back-stack
or Recents entry. The exported launcher is not a trusted notification-payload endpoint.

The original direct-to-exported-launcher candidate required #495's unauthenticated OPEN intake and could
lose taps if landed first. The revised private entry removes that intake dependency. WP-302 still owns
the actual current-session/generation-aware navigation consumer and READY retry. Proposed non-breaking
order: its queue/navigation binding must land first with exported OPEN intake removed or independently
secured; then this private-Activity producer can replace the old broadcast producer. The intermediate
consumer-first state retains the original trampoline limitation but does not intentionally discard
payloads or expose a new notification-input surface. This is a landing plan, not an authorized merge,
completed cross-owner integration, or device acceptance.

The `exported=false` manifest boundary is enforced by Android for external callers; action/data checks or
PendingIntent immutability alone do not authenticate a separately constructed intent to an exported
Activity. Cross-UID rejection, genuine PendingIntent delivery, recreation and API31/37 background/cold
start still require real execution evidence. Existing receiver-only reply/read process-death and
accepted-send cancellation risks remain tracked separately in #514; this repair does not solve them.

Content notifications do not auto-cancel on the platform tap. The private entry
cancels the notification identified by its validated notification-ID URI only
after queue acceptance and launcher handoff. At queue capacity, it still opens
the app but leaves the original platform notification and its PendingIntent
available for another tap after readiness/draining. It neither increases the cap
nor evicts queued replies/mark-read responses. A real content-PendingIntent host
regression fills all 32 slots with alternating reply/read actions, verifies the
notification survives rejection and those actions drain unchanged, then retaps
and verifies destination acceptance and notification removal. This is retained
retry capability, not a claim of immediate navigation on rejection or durable
process storage after queue acceptance. The new capacity case awaits exact-head
hosted execution; the preceding `30024a023` passed run `41417844370` with 17
notification executions but did not cover capacity.

### Unactivated durable-open producer draft

The isolated SQLite candidate adds `NotificationOpenHandoffStore` and payload persistence helpers;
there is no runtime reference from the private Activity, dispatcher or app. It is not a frozen
consumer API or a claim that the published memory-only process-loss gap is closed.
Its suspend operations run on `Dispatchers.IO`, outside lifecycle/navigation locks:

- `initializeNew()` is an explicit bootstrap operation. Its caller must first establish a fresh
  install externally; normal stage/read/ack never create a missing store. This candidate does not
  implement the external known-initialized marker or distinguish total data loss from a fresh install.
  An explicitly authorized fresh bootstrap can retry an empty version-zero SQLite schema left by
  an interrupted initialization transaction; unknown user schema or initialized versions are not
  replaced. Ordinary stage/read/ack still reject that empty file. This is not permission to call
  bootstrap after an initialized store is lost.
- `stage(postId, payload)` transactionally assigns and persists
  `(producerStoreId, postId, deliveryId, sequence)` plus typed payload. A repeated authentic post
  returns the same pending or consumed identity; changed payload is rejected.
- `beginInventory()` and `readInventoryPage(snapshot, afterSequence, limit)` expose pending AND
  retained consumed records in bounded sequence-ordered pages. Every committed stage/ack changes
  the revision, invalidating a mixed scan; missing sequence rows fail rather than claim completeness.
- `acknowledge(identity)` atomically changes pending to consumed, drops the payload and retains exact
  identity/comparison evidence. Repeated exact ack returns `AlreadyAcknowledged`; wrong store,
  delivery or sequence cannot consume another row. This is an independent producer transaction,
  not a consumer receipt or a cross-store transaction.

The candidate separates 32 pending slots from consumed identity retention. It has no tombstone TTL,
eviction or compaction: **this is a non-activated implementation choice, not selected retention
policy**. SHA-256 comparison of encoded routing metadata is provisional storage/privacy design,
not an approved comparison-evidence format. Message bodies, titles and inline reply text are not
stored; routing metadata can still contain room names and identifiers.
Missing, unavailable, corrupt and ambiguous write outcomes are explicit. SQLite corruption handling
does not authorize deletion/recreation; ambiguous commits are reread against the same post/identity.
No ack is retried as a fresh stage. Payload round trips, concurrent duplicate stage, exact idempotent
ack, retained-conflict evidence, missing storage, corrupt storage, inventory gaps and revision
invalidation have authored API31/37 Robolectric tests. Execution status is recorded below.
SQLite-trigger fault tests also abort metadata updates after the row mutation and verify rollback
of stage identity/sequence and ack payload/disposition, followed by same-post/exact-identity retry.
These are real database transaction failures, not evidence of process termination during fsync.

WP-302 confirms neither its navigation CAS nor Android saved state is a durable destination receipt.
Removing a row after only that CAS would reproduce the process-loss window. Consumer integration must
durably commit and restore a delivery-ID-bound destination/consumption receipt before acknowledging
the pending row, report persistence/ack failures and leave stale-session completions pending.
WP-215's wire-action receipt and in-memory `navigationCommitted()` signal do not provide this
guarantee. No dispatcher/receiver changes or consumer-file edits are included in this draft.
Activity activation is held until the receipt/restore contract and delivery-ID transport are
implemented together; the existing #515 process-loss gap remains open.

WP-302 confirms no production route journal or shared-ingress position currently exists. Before
activation, stage must additionally persist a registered, gap-visible ingress position and its
issuer/epoch in the SAME producer transaction. A producer sequence cannot order Back/tab/external
link ingress. Startup must reconcile complete producer/consumer inventories before new commits;
Prepared, unknown journal identity, missing receipts for consumed rows, and unproved manager custody
never authorize ack. Actual published revision binding, later durable navigation supersession,
new-session/radio/entity/READY validation, restorable back-stack consequences and receipt-before-ack
remain consumer/joint integration requirements. No manager writer or consumer edits are introduced.

### Channel display target (separate from receive origin)

The bounded content/reaction repair adds `ChannelNotificationTarget.Proven(radioId,
channelIndex, occupantId)` or explicit `Unproved` to channel/reaction payloads. "Proven" describes
the immutable channel used to DISPLAY the notification, not authenticated RF-message provenance
and never authorization for a quick reply. Payload construction rejects target radio/slot mismatch.
The service channel-post API appends this target; WP-214 owns capturing it from the SAME
`ChannelDTO` used for name/notification level, and WP-302 owns app adapter/navigation integration.
There is no second channel lookup or target sampling in the platform producer. Reactions stay
Unproved because their current source does not establish a trustworthy occupant.

The versioned typed Intent codec writes the display target through the private Activity path.
Missing legacy fields mean Unproved; supplied partial, malformed, unknown-version or radio/slot
mismatched proof is rejected, not downgraded or rebound. Authored host cases send retained A/B/A
content PendingIntents through the actual private Activity and assert each original display target;
other cases cover malformed/legacy proof, persistence round-trip and explicit reaction Unproved.
No new target behavior is accepted merely from authored tests; exact-head hosted execution is
required after composition. Dispatcher ownership, durable OPEN activation and reply-origin
requirements are unchanged.

The initial capacity repair's tag-only cancellation could retire a newer alert
with a reused notification ID. Each built notification and content intent now
shares a fresh post identity. Actual adapter posting and conditional retirement
hold the same process-wide lock around NotificationManager operations; retirement
checks the active post identity inside that boundary before cancelling. A newer
same-tag post therefore survives an older tap, including replacement during
launcher handoff. Tests capture a real PendingIntent launch and use an Activity
shadow to post a replacement after the actual launcher start returns but before
the private entry resumes its retirement operation. No dispatcher or
consumer changes are required. Exact-head hosted execution remains required.

The `5098074aa` candidate passed hosted run `41423661838` (23 notification
executions), but exact-head review identified a remaining asynchronous-publication
race: `notify` can return while `activeNotifications` still exposes the older
post. Retirement now compares the latest successfully submitted post identity
recorded under the same lock as `notify`, not that lagging active snapshot.
Explicit removals clear the submission record under that boundary. An unknown
process history conservatively leaves the platform notification available instead
of cancelling by tag alone. The extra delayed-publication shadow regression
holds B's actual manager publication while exposing A, sends A's real token, and
verifies no cancel is submitted before publishing B. This is a deterministic
host model, not Android-service scheduling or device evidence.

Submission history is an access-ordered cache capped at 256 entries, rather than
unbounded process-lifetime storage for swiped/cleared message IDs. Eviction loses
only permission to automatically retire that older notification: unknown entries
remain visible, and do not erase or override a newer post's protection. A host
test posts/dismisses 300 distinct IDs, asserts the exact 256-entry bound, taps an
evicted original through its real token and checks retention, then replaces it
and verifies the old identity cannot retire the new post. This cache is not
durable delivery or navigation acknowledgement. The `26f14e005` hosted run
`41426499040` failed before execution because the deferred-publication shadow was
nested in the wrong test scope; `ba8844930` corrects its declaration.

The post identity also participates in PendingIntent identity as a URI query
parameter (the logical notification-ID/OPEN path remains unchanged), rather than
only mutable token extras. Independently built posts therefore cannot rewrite a
visible older notification's payload before publication. Tests send A's real
token after B is built but unpublished, then publish B/A in reverse build order
and assert both tokens' payload/post identity remain correct. Existing same-launch
token reuse and hash-collision assertions remain, while independent-post token
expectations now explicitly require isolation. Run `41421371653` for `f940c49a0`
failed test compilation because a Robolectric generic return type was not
specified; the shadow call now explicitly supplies `Unit`. No test pass from
that failed candidate is claimed.

### Snapshot-selected cleanup adaptation

Reply and mark-read broadcast PendingIntents now also compose the content post
UUID into their data identity. Building same-logical-ID B cannot mutate visible
A's payload, including equal message UUIDs on different radios. A real-token host
regression sends A after B builds but before publication, then B, and repeats in
reverse publication order with both RemoteInput reply text and immutable read
actions. The receiver, process queue and frozen WP-302 consumer are unchanged.

Pinned Swift `NotificationService.swift:809-858` snapshots delivered requests and
removes their logical identifiers. Android snapshot-selected contact/channel/room
cleanup now carries an opaque UUID post identity in `DeliveredNotification` and
uses the distinct abstract `removeDeliveredSnapshot` port operation. Outcomes are
explicitly removed, superseded, or unknown identity; the service reports unknown
retention, contains delivery failures and propagates cancellation. The explicit
message-ID operation still intentionally removes the current logical ID.

The adapter selects against its latest successfully submitted identity under the
same lock as posting/removal, including delayed Android publication. Missing,
evicted or process-unknown identity never falls back to unconditional cancel.
