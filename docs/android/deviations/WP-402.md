External contribution, no lease. No device, emulator or Robolectric verification is claimed.
Based on current `origin/main`, including merged WP-401 (PR #152); depends on WP-206 (connectedDevice FGS) and WP-303 (app container).
Swift has no equivalent (iOS shows no ongoing connection notification), so this is Android-only infrastructure.

## What is delivered (`platform/notifications/.../status/`)

| Piece | Role |
| --- | --- |
| `ConnectionStatusMapper` | Pure mapping from the owner's `ConnectionSnapshot` (state, transport, BLE phase, issue) to `ConnectionStatusKind`; chooses the actions. Connection-blocking permission denial (`BLUETOOTH_CONNECT/SCAN`, `COMPANION_ASSOCIATION`) becomes `PERMISSION_NEEDED`; other issues are `FAILED`/`BLUETOOTH_OFF` |
| `ConnectionStatusNotificationFactory` | Ongoing, private-visibility notification with Connect / Disconnect / permission actions. Explicit, immutable PendingIntents; no custom view |
| `ConnectionStatusNotifier` | Renders only. Supplies the notification for the WP-206 `ConnectedDeviceNotificationProvider` and updates it under the foreground service's own id (`0x4d43`) and channel (`connected_device`), so there is exactly one status notification |
| `ConnectionStatusCommandRouter` + `ConnectionStatusActionReceiver` | Notification taps become requests to the existing `ConnectionController` (the runtime `ConnectionManager` role). No transport, session or second controller is constructed |
| `ConnectionStatusAvailability` | Permission fallback decision |
| `LiveUpdateEligibility` | Decides promotion |

## No duplicate connection owner

- The router receives the process's single `ConnectionController` through `attach(controller, targets)` and calls only
  `connect(target)` and `disconnect(USER_REQUEST)`. `target` comes from an app-supplied `ConnectionTargetProvider`
  (the persisted last radio).
- Redundancy is decided by the owner's own snapshot: Connect is ignored unless the owner is `DISCONNECTED`; Disconnect
  is ignored when it is idle and does not want a connection. A second tap while a command runs is ignored.
- Cold start (the receiver may run in a fresh process): only the latest command is kept (opposite commands replace each
  other), for 120 s, then replayed on `attach`; an expired command is dropped. Owner exceptions are contained and logged.
- The notifier never starts or stops the foreground service (WP-206 `ConnectedDeviceHostingController` does).

## Permission fallback

`ConnectionStatusAvailability.evaluate` returns `NOTIFICATION`, `ASK_THEN_IN_APP` (never prompted), or `IN_APP_ONLY`
(denied, app notifications off, or channel blocked). `update` returns `SURFACE_UNAVAILABLE` and never throws, and the
service's start contract is unaffected: `notificationFor` always returns a notification. A missing Bluetooth grant shows
`PERMISSION_NEEDED` with an Allow action when the app supplies `permissionIntent`.

## Live Update (Android 16 QPR1, API 36.1)

Requested (`setRequestPromotedOngoing`, indeterminate `ProgressStyle`, short critical text) only when all hold: API 36.1+,
the status is `CONNECTING` or `SYNCING`, that connect is user-initiated (an automatic reconnect never is), and
`NotificationManager.canPostPromotedNotifications()` is true. A steady `READY`, disconnected, error or permission
state is a standard ongoing notification. Eligibility is re-evaluated on every update, so promotion ends when the
connection settles. Judgment call for review: a mesh link is not one of the platform's canonical Live Update categories
(navigation, rides, calls, timers); the waiting-for-connect window is the only time-bound user-initiated activity, hence
the narrow rule. API 36.0 remains a standard ongoing notification: runtime eligibility uses the full SDK version and
the API-36.1 calls are isolated behind that guard.

## Deviations and gaps (outside WP-402 write paths)

1. App wiring (WP-303/407): register a non-exported `ConnectionStatusActionReceiver`; declare `POST_NOTIFICATIONS` and
   `POST_PROMOTED_NOTIFICATIONS` (API 36); set `ConnectedDeviceServiceHost.notificationProvider = { _, ch -> notifier.notificationFor(ch) }`;
   call `ConnectionStatusCommands.router.attach(controller, targets)`; call `notifier.update` on snapshot changes, passing
   `userInitiated` from the user's own connect request. `FOREGROUND_NOTIFICATION_ID`/`CHANNEL_ID` duplicate the WP-206 constants
   because this module cannot depend on `core:connectivity` (cannot edit its build file); a unit test in the app should assert equality.
2. Localized `ConnectionStatusLabels` (the module has no string resources); activity PendingIntents via
   `ConnectionStatusIntents`. The host supplies the merged `NotificationAuthorizationStatus` contract to the notifier.
3. Widget and Quick Settings tile surfaces belong to other WPs (`platform/widgets`); this WP supplies only the shared
   `ConnectionStatusKind` mapping and the availability decision they can reuse.
4. `src/test` is outside the write paths and `androidTest` has no JUnit, so
   `ConnectionStatusTests` is dependency-free, compile-only, and exposes `cases`. The 12 cases compile in
   `compileDebugAndroidTestKotlin`; execution is not claimed. The module's six merged WP-401 JVM tests remain green.
5. Not verified: real Live Update promotion, notification rendering, action delivery on a device.

Source/test parity: no Swift test maps to this layer. Original-case inventory approval (WP-004) is pending, so completion is not asserted.
