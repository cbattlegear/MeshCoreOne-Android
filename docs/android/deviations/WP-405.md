# WP-405 deviations

## Mounted held-join observations and remaining startup boundary

The four held-join methods run the real adaptive shell. Expanding mounts the
Chats root alongside the conversation. `ChatsListRoot` observes
`pendingChannel`; `ChatListActions.handlePendingChannelNavigation` opens its
route and then clears that transient handoff. `NavigationCoordinator.openChat`
is idempotent for the already-selected top conversation. The handoff is not
the lasting selection, and asserting its ID after the mounted effects settle
is incorrect. The methods now observe bounded consumption, the exact selected
channel and top destination, preserved prior stack entries/other tab stacks,
and the mounted entry's actual editable composer. They still require the
original metadata, replacement identity, disabled submitting state, single
dialog, no pre-consent write, exact packet, and one write per consent.
No routing or map production behavior changes for this correction.

Cold-start support paths admit `modify-related-consumer` on trusted main
`5878b5357dc9fe9986f002fe68763aca0bc35303`. Supported same-owner advisory
bookkeeping reached revision 13 without rebinding the historical identity or
base. That is not a controller receipt or startup implementation.

The remaining startup phase is not a cache-read-only barrier:
`AppState.handleReturnToForeground` awaits `checkWiFiConnectionHealth` and
the queued `appDidBecomeActive`. Both runtime paths can initiate/await a
WiFi or simulator connection; the health path also performs stale-transport
teardown. Waiting for that whole operation can block offline navigation on
physical connection, while draining immediately after cache initialization
can precede its teardown. `enqueueBleTransition` exposes a `Job`, whose
`join` is not a successful foreground outcome. The independently refreshed
`ConnectionManagerAppPort.cached` is not protected by the manager lock.
A correct composition needs a radio-independent persisted-cache/store result
and an explicit successful initial teardown/provenance boundary, distinct
from reconnect completion and with failure, cancellation and retry.
The existing held WP-302 manager/registry/container/navigation producer
boundary must be reconciled before using it. No cache-only gate, standalone
validity predicate, unmerged API, or startup success is authored here.
The startup schedules and required regressions remain unexecuted.

The singleton dialog relocation does not extend the conversation composer's
lifetime. `AppChatsContent` still keys the conversation subtree by its
selection, uses a composition-owned coroutine scope, and closes the timeline
on disposal. The separate #524 composer cancellation/commit-before-return
finding is not repaired or verified by these confirmation tests.

## Issue #417: independent confirmation identities and one adaptive host

Pinned `NavigationCoordinator.swift` and `ChatLinkRouter.swift` retain two
independent optional channel/hashtag requests: same-kind staging replaces,
not queues, and `ChatsConversationSheets.swift` clears the particular sheet's
binding. Android retains those semantics. Every staging now wraps its complete
payload in a fresh UUID delivery identity, including identical-payload
replacements; the existing payload getters remain available. No queue is added.
The dialog acknowledges only its displayed identity, and successful completion
acknowledges and navigates in one coordinator CAS. A stale completion cannot
clear or navigate over its same-kind replacement. The other kind remains
pending; it does not suppress a valid completed join's navigation or erase the
real radio write.

The real adaptive shell owns one channel/hashtag dialog outside its per-entry
root/detail composition. Both optional slots retain a holder keyed by their
own identity and current radio, so an independent arrival, temporary
channel-priority preemption or resize does not recreate an in-flight holder.
Loading is still an effect and radio writes still require explicit consent.
The existing channel-first presentation precedence is unchanged.

This is a consumer-only repair. WP-302 owns the shared manager -> registry ->
container -> navigation commit boundary after the genuine #506 transition;
WP-405 will wire external/chat channel/hashtag initiation, lookup completion
and confirmation/write ownership only after that boundary is actually
accepted and integrated. No unmerged #495 API or check-then-effect predicate
is copied. Same-radio/new-session and different-radio held-lookup schedules
remain unexecuted and unresolved; pre-connection delivery must survive the
eventual integration. Same-radio `AppChatsFeature.session(radioId)` can resolve
a successor, so identity-safe UI acknowledgement alone is not session-safe
write ownership.

Future composition with #495 must preserve its singleton `AppPendingContact`
and `AppPendingRoomAuthentication` shell hosts, navigation state-store
publication protocol, contact provenance/revision and retirement semantics.
The channel slot identity fields replace only the corresponding payload
storage and explicit clears; no lifecycle acceptance is implied.

## Issue #504: suspended external-delivery replacement

The frozen Swift staging call is synchronous. Android routing can suspend in a
contact/channel lookup, so a newly submitted delivery must invalidate the older
operation before the replacement enters the router. A distinct delivery ID now
retires and cancels the prior structured routing child at submission and takes
the routing slot immediately. This also applies to identical URI text with a
new delivery ID; a repeated ID remains a duplicate. The bounded 64-ID history
includes superseded deliveries. An obsolete submit returns `Superseded`, not a
success-shaped routing outcome.
Staging and claiming the routing child share one mutex transaction, so a
concurrent submitter cannot claim another delivery in its own caller scope.

The App router checks its coroutine's cancellation before effects and after
each suspended lookup. A delivery-scoped coroutine-context guard serializes
submission invalidation with synchronous navigation writes and selection of the
confirmation host. External routing no longer selects Chats speculatively before
a suspended lookup, and rejected routing never changes selection or back stacks.
Unlike Swift's synchronous dispatch, Android waits for a lookup before deciding
whether to navigate or stage consent. Selecting the host in the same navigation
state update as a confirmed external staging write preserves the Chats host without an
obsolete temporary selection or a rollback that could overwrite user navigation.
Existing-contact/channel and map destinations select their own tab directly;
an ignored external self-contact retains the original completed Chats selection.
This intentionally changes only the pending-lookup selection timing, not consent,
metadata, successful destinations or the in-chat routing host.
The guard never spans a suspended
lookup and does not rely on caller thread confinement. The environment forwards
an explicit external-host flag to the three staging methods; their default
preserves internal/clearing behavior. Selection and request metadata publish as
one StateFlow value, not two writes under a reentrant JVM monitor. Thus a
collector that submits B upon seeing Chats cannot retire A between selection
and staging. No new lock, dispatcher, unowned scope, connection or public
ordering API is introduced. These checks
complement, rather than replace, WP-302's
independent contact-session/radio/generation and producer-ordering work.
In particular, WP-302's separately reported session-check/navigation-CAS versus
radio-teardown boundary remains unresolved here; this is not lifecycle
acceptance or an implementation of its unmerged PR #495. Eventual composition
must guard synchronous lookup initiation/provenance capture as well as the
whole completion/outcome, and fold external contact selection into that same
successful completion CAS. The later lifecycle/publication lock analysis remains
unresolved outside this standalone repair.
Caller cancellation still propagates and releases only its own slot. Before a
target commit, it preserves the pending delivery for explicit retry. Once a
target write has completed, that fact is recorded inside the delivery guard;
cleanup waits for its owned child outside all locks and consumes the committed
ID non-cancellably instead of making the effect replayable. This is completion
bookkeeping, not an uncancellable lookup or suppressed caller cancellation.
Failures still propagate.
Superseded cleanup cannot drop a newer pending delivery.

Deterministic regression definitions exercise `PendingExternalRoute` through
the actual `AppDeepLinkRouter` and `NavigationCoordinator`, with a controllably
suspended persistence boundary. They distinguish known-contact navigation from
unknown-contact confirmation, identical URI/new ID from duplicate ID, the
before-B-router window, non-cooperative lookup completion, channel/hashtag
replacement and unchanged private-secret/scope metadata. These are JVM consumer
test definitions, not Room/device evidence. Their execution remains pending;
the earlier WP405-LINKS pass below does not verify this repair.

The additional selection regressions start with actual Settings/contact stacks
and a rail-mode tool detail. They require invalid B after suspended A to preserve
the complete navigation state, preserve every later user tab choice, retain an
already committed contact result, and let valid map/channel/hashtag/identical-URI
replacements select their own destination without changing unrelated stacks.
At rail width minus one, exactly the rail threshold and threshold plus one,
rejected URIs retain tool detail and Back behavior; a genuinely committed switch
still applies the existing rail tool cleanup. An unconfined real StateFlow
collector submits B reentrantly as A publishes Chats, requiring the full
confirmation metadata to be present in that first publication and no later A
write. Internal routing and clearing keep their existing selection semantics.
The original supersession/cancellation assertions remain unchanged. These new
definitions are unexecuted until the next exact-head hosted run.
