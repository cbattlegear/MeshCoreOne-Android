## Source and actual consumer

The pinned `ChatViewModelReactionIndexingTests.swift` has four families: DM scope,
channel scope, persistent duplicate guard, and unknown outgoing channel sender.
`ChatTimelinePopulator.indexMessagesForReactions` consumes the existing service,
uses `reactionTimestamp` for DM and `timestamp` for channel messages, selectively
skips unknown names, persists scoped reactions, and updates/rebakes by message ID.
No reference drift was found in the inspected source/test files.

Current main already calls `ChatTimelineDependencies.prepareMessages` on open,
refresh and older-page fetches. `AppChatsFeature.timeline` resolves the matching
conversation-radio session and calls `prepareTimelineMessages`, which indexes
through its `ReactionService`, checks `reactionExists`, persists through the
process-owned Room store, and returns refreshed DTO summaries. Live sync and the
feature-only DTO policy are not this fetched-history trigger.

The remaining defect is in `ChatViewModel.loadOlder`: offset shifts can fetch a
row already loaded. Replay persists its reaction, but the subsequent existing-ID
filter discarded its updated summary. The fix merges prepared summaries into
retained rows while preserving all other loaded metadata and older-page semantics.
It does not delete database rows or add a new parser, queue, store or service.

## Discriminating regression scenarios

`HistoryReactionReplayTest` adds nine methods to the existing App test source set:

- Six methods drive real App timeline open/refresh/loadOlder separately for DM and
  channel history. Each asserts actual Room reaction fields, stored and shared
  coordinator summaries, a rendered reaction fragment, repeat-queue persistent
  row identity, and retention of a different contact/channel's pending reaction.
  DM sender timestamp differs from corrected timestamp; expected hash is the
  existing independent `Hello`/1704067200 wire vector `b45pc4ek`, not generated by
  the candidate hash implementation.
- Two offset-overlap methods load 50 of 51 stored rows, queue a reaction for the
  oldest loaded target, insert a newer stored row without a live event/refresh,
  then load older. The old algorithm saves the reaction but retains a null
  mounted summary. Assertions require both the persisted and visible summary,
  unique loaded identities, the older row, no implicit newest-row refresh, and
  the real shared rendered reaction fragment.
- One method uses the actual App replay helper with an explicitly unknown local
  name: outgoing/unknown incoming rows remain present and untouched, the later
  known incoming row still replays, and a subsequent known local name drains the
  retained outgoing reaction into the real store. This case is helper-level,
  not a claim that the connected App normally lacks its node name.

The actual session graph uses the repository fake radio and a native-SQLite
Robolectric Room harness at API 31. No physical radio, Android device, iOS run,
TalkBack, screenshot, signing or release evidence is claimed.
