## Actual producer and consumers

Located contact detail -> optional `NodesNavigation.openLineOfSight` capability
-> `NavigationCoordinator.navigateToLineOfSight` -> contact-bearing
`NavigationDestination.Tool` -> actual shell -> `LineOfSightEntry` -> existing
`LineOfSightStateHolder` initializer. No feature-to-feature dependency is added.
The host binds the action only when LOS dependencies are available; unlocated
contacts do not offer it. It remains enabled while disconnected and uses the
existing localized tool label and a 48dp minimum target.

Mounted API31/37 nodes controls invoke the actual contact-detail action and assert
the exact DTO, enabled state, touch target and absence of radio commands. Mounted
API31/37 App controls use the real shell and entry (not substituted content),
assert original inputs, clear then recompose without reseeding, and open the
plain tool after a selected-contact entry without stale selection. Navigation
restoration retains the tool but not the identity-bearing contact. JVM tests use
the production unsupported-map path; they do not prove native map rendering.
Endpoint elevations are synthetic fixture values, not new RF numerical evidence.

The independent review found that retained navigation could reapply a cleared
contact after Activity recreation. An entry-owned saveable Boolean now records
that Point A was edited or cleared, so a replacement holder does not replay that input.
Only that Boolean is saved, not the contact DTO or its identity/location. An
additional actual `ActivityController.recreate()` regression retains the
contact-bearing destination, replaces the Activity, remounts the real shell and
requires both endpoints to stay empty with no second elevation request. Existing
recomposition and plain-entry controls remain unchanged.

A subsequent review identified relocation without an intermediate null endpoint
and clear/reselection conflation. Consumption is now recorded synchronously by
the holder's Point A mutation boundary, not inferred from asynchronously collected
state. Constructor seeding bypasses that edit notification. The entry's internal
holder-owning composable is shared with API31 mounted panel controls that actually
recreate a saved-state-owning Activity: Relocate followed by the real map-coordinate
handler, clear and same-contact reselection in one main-thread turn, and untouched
preselection. The JVM control delivers the map coordinate directly; it does not
claim native map projection. The existing App API31/37 real-shell recreation
control remains in place. No contact data is saved and no test helper becomes public.
